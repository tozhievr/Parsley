# Parsley — архитектура DSL для описания грамматик

> Historical architecture proposal, not a product specification. The supported target is C17 only. Multi-language backends, independent LALR/GLL runtimes and parse forests below are design ideas, not delivered behavior. Current contracts: [STATUS.md](STATUS.md), [REGEX.md](REGEX.md).
> Исторический проектный документ. Единственный поддерживаемый таргет — C17; перечисление других языков и алгоритмов ниже не означает их наличия в продукте.

Статус: черновик v0.1 · Назначение: проектирование Haskell-подобного языка описания грамматик и генератора парсеров на его основе.

## 1. Цели и не-цели

**Цели**

- Грамматика читается как обычный Haskell-модуль: сигнатуры, `data`, каррирование, `<$>`/`<*>`, `do`, layout вместо скобок и точек с запятой.
- Один исходник, много бэкендов (Haskell, Rust, TypeScript, Python и др.) и несколько алгоритмов разбора.
- Грамматика статически анализируема: FIRST/FOLLOW, левая рекурсия, неоднозначности, мёртвые правила.
- Типизированный результат: AST выводится из правил, а не пишется вручную дважды.
- Ошибки компилятора грамматик уровня GHC/Elm: с контекстом, подсказками и примерами.

**Не-цели**

- Parsley не является языком общего назначения и не интерпретирует произвольный Haskell.
- Семантические действия не превращаются в полноценный язык: только чистые выражения и конструкторы данных.
- Не заменяет парсер-комбинаторы в рантайме: цель — генератор, а не библиотека.

## 2. Как это выглядит

```haskell
module Calc (program) where

import Parsley.Prelude (sepBy, many, eof)

-- Лексика ---------------------------------------------
skip  ws      = /[[:space:]]+/
skip  comment = /--.*/
token number  = /[0-9]+([.][0-9]+)?/   :: Double
token ident   = /[a-z_][a-zA-Z0-9_]*/  :: Text
keywords      = ["let", "in"]

-- AST (выводится в целевой язык) ----------------------
data Op = Add | Sub | Mul | Div | Pow

data Expr
  = Num  Double
  | Var  Text
  | Neg  Expr
  | Bin  Op Expr Expr
  | Call Text [Expr]
  | Let  Text Expr Expr

-- Синтаксис -------------------------------------------
program :: Expr
program = expr <* eof

expr :: Expr
expr = operators atom
  [ infixl 6 ["+" => Bin Add, "-" => Bin Sub]
  , infixl 7 ["*" => Bin Mul, "/" => Bin Div]
  , infixr 8 ["^" => Bin Pow]
  , prefix  9 ["-" => Neg]
  ]

atom :: Expr
atom
  =  Num  <$> number
  |  Call <$> ident <*> parens (expr `sepBy` ",")
  |  Var  <$> ident
  |  parens expr
  |  letExpr

letExpr :: Expr
letExpr = do
  "let"
  x    <- ident
  "="
  e    <- expr
  "in"
  body <- expr
  pure (Let x e body)

parens :: Rule a -> Rule a
parens p = "(" *> p <* ")"
```

Что здесь происходит неявно: строковые литералы (`"("`, `"let"`) автоматически становятся анонимными токенами с приоритетом выше регулярных (поэтому `let` не становится `ident`); общий префикс `Call`/`Var` выносится за скобки автоматически (left-factoring); таблица `operators` разворачивается в стратифицированную грамматику или precedence-climbing, в зависимости от бэкенда.

## 3. Принципы дизайна

1. **Правила — значения, параметризованные правила — функции.** `parens`, `sepBy`, `many` — не макросы, а обычные определения с сигнатурами `Rule a -> Rule b`. Это даёт библиотеку переиспользуемых кусков грамматик.
2. **Applicative по умолчанию, Monad по явному согласию.** Грамматика, использующая только `<$>`, `<*>`, `<|>` и `do`, в котором результаты привязок не влияют на то, какой разбор пойдёт дальше, статична и компилируется в таблицы или автомат. `do` desugar-ится как ApplicativeDo. Зависимость структуры от значения возможна только в блоке `context` (см. 4.7) и ограничивает набор бэкендов.
3. **Типы вместо магии.** У каждого правила есть тип результата. Если сигнатуры нет, она выводится; в публичном API модуля она обязательна.
4. **Лексика и синтаксис — один язык.** Токены, режимы лексера и правила живут в одном файле и ссылаются друг на друга.
5. **Layout вместо знаков препинания.** Отступы значимы, как в Haskell; `|` в начале строки продолжает определение.
6. **Хорошие значения по умолчанию, явные рычаги.** Приоритет токенов, ассоциативность, режим разбора — по умолчанию разумные, но переопределяются прагмами.

## 4. Языковая модель

### 4.1 Модули и импорты

Модуль — единица компиляции и пространство имён. Поддерживаются экспортный список, `import qualified`, `hiding`. Грамматики можно наследовать и расширять: `import Json as J` и затем `J.value <|> myExtension`. Циклические импорты запрещены, рекурсия правил внутри модуля разрешена.

### 4.2 Лексика

| Конструкция | Назначение |
| --- | --- |
| `token name = /regex/` | Именованный токен; тип по умолчанию — `Text`, переопределяется через `:: T` |
| `skip name = /regex/` | Токен, отбрасываемый лексером (пробелы, комментарии) |
| `keywords = [...]` | Зарезервированные слова; побеждают идентификаторы при равной длине |
| `mode name where ...` | Режим лексера (строки, интерполяция, вложенные комментарии) |
| `"literal"` в правилах | Анонимный токен; регистрируется автоматически |

Разрешение конфликтов — «максимальное вхождение, затем приоритет, затем порядок объявления». Конфликты, которые невозможно разрешить, — ошибка компиляции, а не тихое поведение.

```haskell
mode string where
  token chars  = /[^"]+/
  token escape = /[\\][nrt"]/
  token close  = "\"" -> pop

token open = "\"" -> push string
```

### 4.3 Типы данных

`data` и `newtype` объявляются прямо в грамматике и транслируются в идиоматичные типы целевого языка: ADT → `enum`/`sealed class`/`union`. Можно подключить существующий тип: `foreign data Expr = "ast::Expr"`. Записи (`data P = P { name :: Text, age :: Int }`) используются для именованных полей в `do`-блоках.

### 4.4 Правила и комбинаторы

Правило: сигнатура плюс определение. Ядро комбинаторов:

| Комбинатор | Смысл |
| --- | --- |
| `p <*> q`, `p *> q`, `p <* q` | Последовательность (с сохранением результатов или без) |
| `p <\|> q` или строка с `\|` | Упорядоченный/неупорядоченный выбор (зависит от режима, 7) |
| `many`, `some`, `optional` | Повторения |
| `sepBy`, `sepEndBy`, `between` | Списки и обрамление |
| `lookahead p`, `notFollowedBy p` | Предпросмотр без потребления |
| `p <?> "expression"` | Метка для сообщений об ошибках |
| `recover p sync` | Восстановление после ошибки по синхронизирующему токену |

Форма `do` — синтаксический сахар для последовательности с именованными результатами. Форма `Ctor <$> a <*> b` — для коротких правил.

### 4.5 Приоритеты и ассоциативность

Блок `operators atom [...]` принимает базовое правило и список уровней в стиле `infixl`/`infixr`/`infix`/`prefix`/`postfix`. Порядок записи не важен, значение определяет число. Вызовы (`f(x)`), индексация (`a[i]`) и тернарный оператор описываются через `postfix` и `mixfix`:

```haskell
  , postfix 10 [call, index]
  , mixfix  1  ["?" expr ":" => Cond]
```

### 4.6 Параметризованные правила

Правило может принимать правила и значения как аргументы. Компилятор выполняет мономорфизацию: каждое применение `parens expr` порождает отдельное специализированное правило, поэтому анализ и генерация остаются первого порядка. Рекурсия через параметры без «защиты» токеном — ошибка (бесконечное разворачивание).

### 4.7 Контекстная чувствительность (opt-in)

Для случаев вроде отступов, heredoc, тегов с совпадающим закрытием:

```haskell
htmlTag :: Node
htmlTag = context do
  name <- "<" *> ident <* ">"
  body <- many node
  "</" *> exactly name <* ">"
  pure (Elem name body)
```

`context` включает монадическую семантику и допускается только для бэкендов с поддержкой (PEG/комбинаторные/GLL). Для остальных — диагностика с объяснением.

### 4.8 Тесты и примеры в самой грамматике

```haskell
example "арифметика"   : "1 + 2 * 3"  parses-to  Bin Add (Num 1) (Bin Mul (Num 2) (Num 3))
example "ошибка"       : "1 +"        fails-at   (1, 4) expecting "expression"
```

`example` выполняются на этапе компиляции и входят в документацию. Это основа регрессионного тестирования и property-based fuzzing по грамматике.

### 4.9 Прагмы

`{-# START program #-}`, `{-# MODE LALR #-}`, `{-# BACKEND rust #-}`, `{-# PREC ident < keyword #-}`. Прагмы никогда не меняют язык, только стратегию генерации.

## 5. Архитектура компилятора

```text
 source.parsley
      │
  [1] Lexer/Layout     — токены самого DSL + вставка виртуальных скобок
      │
  [2] Parser           — Surface AST (сохраняет позиции и комментарии)
      │
  [3] Name resolution  — модули, импорты, области видимости
      │
  [4] Type checking    — HM-вывод для Rule a, проверка ADT, ApplicativeDo
      │
  [5] Desugar          — do → Applicative, operators → Prec-узлы,
      │                  мономорфизация параметризованных правил
      │
  [6] Core Grammar IR  — первый порядок, без сахара, с типами
      │
  [7] Analysis         — FIRST/FOLLOW, левая рекурсия, left-factoring,
      │                  неоднозначности, недостижимые правила
      │
  [8] Strategy select  — LL(k)/ALL(*) · LALR/LR · PEG/Packrat · GLR/GLL
      │
  [9] Backend codegen  — Haskell · Rust · TypeScript · Python · …
```

Каждая стадия — чистая функция `Input -> Either [Diagnostic] Output`. Диагностики накапливаются, а не обрываются на первой ошибке. Это даёт восстановление и удобство для LSP.

## 6. Core Grammar IR

IR — единственный контракт между фронтендом и бэкендами:

```haskell
data Grammar = Grammar
  { gTokens :: [TokenDef]
  , gModes  :: [LexMode]
  , gRules  :: Map RuleId Rule
  , gStarts :: [RuleId]
  , gTypes  :: [DataDecl]
  }

data Rule = Rule { rType :: Type, rBody :: Prod, rSpan :: Span }

data Prod
  = Tok TokenId
  | Ref RuleId
  | Seq [Prod]
  | Alt [Prod]
  | Rep Int (Maybe Int) Prod
  | Look Polarity Prod
  | Act Action [Prod]     -- чистое действие над результатами
  | PrecTable Atom [Level]
  | Ctx ContextProd       -- только для бэкендов с поддержкой
```

IR сериализуется в JSON/S-expr: это позволяет писать сторонние бэкенды и анализаторы без доступа к коду компилятора.

## 7. Анализ и выбор стратегии

Компилятор определяет, к какому классу относится грамматика, и выбирает алгоритм, если пользователь не задал его прагмой:

- **LL(1)/LL(k)** — если нет конфликтов; быстрейший и самый читаемый код.
- **LALR/LR** — когда нужны левая рекурсия и таблицы.
- **PEG/Packrat** — выбор `|` упорядочен; нужно для `context` и предсказуемого поведения.
- **GLR/GLL** — для неоднозначных языков; результат — лес разборов или набор вариантов.

При конфликте выдаётся **объяснение с контрпримером**: конкретная входная строка, два дерева разбора и предложение исправления (приоритет, left-factoring, смена режима).

## 8. Бэкенды

Бэкенд — модуль с интерфейсом `Grammar -> Options -> [File]`. Обязательства: сгенерировать типы из `gTypes`, лексер, парсер, API `parse :: Text -> Either ParseError a` и сообщения об ошибках с позициями и ожидаемыми токенами. Опционально: инкрементальный разбор, CST с trivia, tree-sitter-вывод, подсветка синтаксиса и LSP-сервер.

Одна из ключевых идей — **общий набор конформанс-тестов**: все примеры из `example` прогоняются на каждом бэкенде, и результаты сравниваются побайтово.

## 9. Диагностика

```text
error[E0214]: ambiguous alternatives in rule `atom`
  --> Calc.parsley:28:5
   |
28 |   |  Call <$> ident <*> parens (expr `sepBy` ",")
29 |   |  Var  <$> ident
   |      ^^^^^^^^^^^^^^ both start with `ident`
   |
   = note: this is resolved by left-factoring (automatic)
   = help: add {-# NOFACTOR #-} to disable and see the conflict
```

Принципы: показывать исходный фрагмент, объяснять причину в терминах грамматики (не таблиц LR), предлагать конкретное исправление и давать стабильные коды ошибок.

## 10. Инструментарий

- **CLI**: `parsley build`, `check`, `test`, `explain E0214`, `fmt`, `graph` (railroad-диаграммы и DOT).
- **Форматер** с единственным каноническим стилем, как `ormolu`.
- **LSP**: подсветка, переход к определению правила, «найти использования», inline-диагностика, вывод типов правил при наведении.
- **Playground**: вставляешь вход и видишь дерево разбора и конфликты в реальном времени.
- **Менеджер пакетов** для библиотек грамматик (`Parsley.Prelude`, `Parsley.Unicode`, `Parsley.Layout`, `Json`, `Sql`).

## 11. Дорожная карта

1. **MVP**: лексер + Applicative-правила + `data` + LL(1) + бэкенд Haskell + `example`.
2. `operators`, левая рекурсия, LALR, второй бэкенд (Rust или TypeScript).
3. Режимы лексера, восстановление после ошибок, форматер, LSP.
4. `context`, PEG, GLR; инкрементальный разбор.
5. Экосистема: пакеты, playground, импорт существующих грамматик (ANTLR, tree-sitter, BNF/EBNF).

## 12. Открытые вопросы

- Нужен ли отдельный синтаксис для CST (сохранение пробелов и комментариев) или это режим бэкенда?
- Как выражать семантические действия, чтобы они переносились между языками: фиксированный набор примитивов или `foreign`-вставки?
- Следует ли разрешить пользовательские `Applicative`-интерпретаторы поверх грамматики (например, генерация pretty-printer из той же грамматики)?
- Стратегия версионирования IR и обратной совместимости бэкендов.
- Политика Unicode: нормализация, классы символов и границы слов в лексере по умолчанию.

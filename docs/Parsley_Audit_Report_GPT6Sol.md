# Parsley — независимый технический аудит исходного кода

**Дата:** 16 ноября 2026 года  
**Объект:** предоставленный архив `Parsley.zip` (не произвольное состояние `main` или GitHub Releases)  
**Основная версия компилятора:** `1.3.0` (`VERSION`)  
**Версия расширения VS Code:** `1.6.0` (`editors/vscode/package.json`)  
**Статус:** глубокая статическая ревизия с локальными воспроизведениями отдельных дефектов; **полная сборка и все интеграционные тесты не выполнялись** из-за несовместимой версии CMake в среде проверки.

> **Принцип аудита.** Замечания ниже относятся к конкретному содержимому переданного архива. Подтверждённый дефект в исходнике, доказанный отдельным экспериментом эффект, риск при заданных условиях и несоответствие проектной документации — **разные уровни утверждений**. Неудавшаяся конфигурация сборки на этом компьютере **не означает**, что CI проекта не проходит.

## 1. Резюме для автора

Parsley — не демонстрационная оболочка вокруг генератора регулярных выражений. В архиве присутствуют полноценный модульный компилятор (лексер DSL, парсер, AST, разрешение имён, типизация, десахаризация, IR, анализ), интерпретатор грамматик, C17 codegen, отдельный слой семантики PSL, LSP/JSON-RPC, VS Code/Cursor extension, примеры грамматик, тесты, CI и релизные workflow. Интеграция C17 с несколькими системами сборки и общая идея «DSL → самостоятельная библиотека без runtime-зависимости от C++» — сильная продуктовая сторона.

**Но в текущей реализации есть технические долги, которые нельзя закрыть только зелёным CI.** Самые существенные: некорректное C-экранирование некоторых строк, потеря точности `Int` в публичном C17 AST, аварийное поведение при отказе аллокатора, расхождение контекстного и обычного лексического сопоставления, неверные позиции LSP для UTF-8, ограничители стека контекстов и режимов без ошибки, а также заявленный в архитектуре выбор различных алгоритмов разбора, который фактически не ведёт к соответствующим независимым backend-алгоритмам.

**Приоритет инженерных работ:** сначала достоверность генерируемого кода и обработка отказов (P0), затем соответствие грамматической семантики и клиентских протоколов (P1), потом ускорение NFA/PSL и расширение тестирования (P2). Масштаб проекта оправдывает отдельный conformance/differential test suite; без него исправления компилятора будут легко создавать расхождения между интерпретатором и сгенерированным C17.

### 2.1. Уровни доказательности

- **П** — прямо подтверждено чтением кода: ветвление, отсутствие проверки, фиксированный предел, формирование вывода.

## 4. Замечания: корректность генерируемого C17

### F-01 — Неверное экранирование двоичных строк (`P0`, П+Э)

**Место:** `src/codegen.cppm:162–197`, особенно `:182–189`.

Функция `c_string_lit()` преобразует байты `0x00` в `\\0`, остальные непечатные байты — в `\\xHH`. **В C17 hex escape продолжается, пока встречаются шестнадцатеричные цифры**, а octal escape может съесть до трёх цифр. Поэтому байты `0x01, 'A'` кодируются как текст C `"\\x01A"`, который C-компилятор интерпретирует как `0x1A`, а не `0x01` и `'A'`.

**Изолированная проверка (реально выполнена):**

```c
#include <stdio.h>
int main(void) {
    const unsigned char s[] = "\x01A";
    printf("sizeof=%zu, first=0x%02x\n", sizeof s, s[0]);
}
```

Результат: `sizeof=2, first=0x1a`; требовалось `sizeof=3`, байты `01 41 00`. Влияние: неверные литералы в сгенерированных правилах, именах токенов, примерах, пользовательских строках и потенциально сбои компиляции при выходе за допустимый диапазон escape.

**Исправление:** выводить *все* специальные байты через **ровно три octal-цифры** (`\\001`, `\\000`), либо закрывать и открывать C-строку после каждого `\\xHH` (`"\\x01""A"`). Для UTF-8 оставить байтовую идентичность; не пытаться переписывать непечатные байты как Unicode code points.

**Тест:** для каждой пары `a,b ∈ [0,255]` сгенерировать C17-код с literal и сравнить `sizeof`/`memcmp` с исходной последовательностью. Отдельно NUL, `0xFF` + `F`, `\\0` + `7`, CR/LF, кавычки, обратные слеши. **Это реальный блокер для byte-preserving code generation.**

### F-02 — `Int` теряет точность из-за double (`P0`, П+Э)

**Место:** `src/codegen.cppm:865–871`, `:1385–1389`, `:1659–1671`, `:2839–2846`.

В генерируемом `ParsleyValue` существует только `double number_val` + `bool is_int`. При лексическом разборе `Int` выполняется:

```c
long long iv = strtoll(tmp, NULL, 10);
return pv_number((double)iv, true);
```

При конвертации в типизированное поле `int64_t` используется обратное приведение `number_val` к `int64_t`. Значение `9007199254740993` (`2^53+1`) в IEEE-754 binary64 превращается в `9007199254740992` — **значение AST меняется**. Это проверено отдельной C++ программой в текущем окружении. `strtoll` также не проверяется по `errno=ERANGE`/`endptr`, что усложняет диагностику переполнения и некорректных литералов.

**Исправление:** числовое значение сделать tagged union `int64_t i64; double f64` со строгим `kind` / `is_int`; для `Int` парсить с проверкой диапазона, для `Double` отдельно. Не смешивать типы при формировании ADT/JSON/LSP и форматировании. При выходе за диапазон — явная ошибка разбора, не UB от конверсии `double` вне диапазона `int64_t`.

**Тесты:** `0`, `-0`, `±(2^53±1)`, `INT64_MAX`, `INT64_MIN`, `INT64_MAX+1`, ведущие нули, знаки и нечисловой суффикс. Проверить round-trip `parse → C typed AST → formatter`.

### F-03 — Обработка OOM недостаточна в генерируемой библиотеке (`P0`, П)

**Место:** `src/codegen.cppm:1400–1441`, `:1458–1477`, `:1567–1577`, `:1942–1945`, `:1979–1984`, `:2685–2701`.

Примеры из шаблона генерируемого C17:

```c
v->items = (ParsleyValue**)p_malloc(sizeof(ParsleyValue*) * count);
memcpy(v->items, items, sizeof(ParsleyValue*) * count);
```

```c
p->tokens = (ParsleyLexedToken*)realloc(p->tokens,
                                         sizeof(ParsleyLexedToken) * cap);
```

Здесь `NULL` не проверяется. Присваивание результата `realloc` сразу в старый указатель также **теряет доступ к прежней аллокации** при отказе. Аналогичные проверки отсутствуют у нескольких временных NFA-буферов и массива записей левой рекурсии. Умножения `count * sizeof(T)` и удвоение `cap` могут переполнить `size_t`. Под нагрузкой это превращает возвращаемую ошибку парсинга в падение, потерю памяти или повреждение логики.

**Исправление:** единый checked allocator (`checked_mul`, `reserve_array`) с временным указателем `tmp = realloc(ptr, bytes)`, обработкой `NULL`, отдельным `PARSLEY_ERR_OOM` и гарантированной очисткой. Добавить путь ошибок от `pv_list`/`pv_clone` к `ParsleyResult`, а не возвращать частично построенный AST как успешный. Обязательный fault-injection тест с отказом каждой n-й аллокации; ASan/UBSan/LSan в CI.

**Уточнение:** это серьёзная ошибка надёжности/безопасности обработки памяти, но **эксплуатируемость для RCE не установлена**.

### F-04 — Контекстный лексер нарушает принцип maximal munch (`P1`, П+У)

**Место:** `src/codegen.cppm:1955–1977` против `:2099–2115`; аналогично `src/eval.cppm:1250–1279` против `:1414–1426`.

Полный lexer (`p_lex_all`) выбирает кандидат **сначала по длине совпадения**, затем по приоритету. Но в `scannerless` режиме `p_match_token` просматривает конкурентов только с **более высоким приоритетом**; более длинный токен с меньшим приоритетом не запрещает совпадение короткого. Значит общее правило «максимально длинный токен» перестаёт действовать в грамматиках с `context do`.

**Минимальный сценарий для end-to-end проверки:** keyword `"if"`, токен `identifier = /[a-z]+/`, вход `"iffy"`, контекстный путь, пытающийся прочесть keyword. Полный lexer обязан выбрать `identifier` длины 4; scannerless может принять keyword длины 2. Точный тест должен быть оформлен грамматикой с `context do` и допустимыми правилами языка; без запуска бинарника сценарий отмечен как **условный**.

**Исправление:** общая функция выбора lexical winner в обоих режимах: `(match_length DESC, priority DESC, declaration_order ASC)` по всем доступным определениям режима, а `p_match_token` успешен только если выбранный winner — ожидаемый токен. Проверить skips и mode actions.

### F-05 — Не проверяется полное потребление regex-паттерна (`P1`, П)

**Место:** `src/codegen.cppm:275–296`, `:316–326`; `src/eval.cppm:385–401`, `:411–423`.

Обе реализации `RegexParser::parse()` возвращают `parse_alt()`, **не проверяя**, дошла ли позиция парсера до конца паттерна. `parse_seq()` прекращает чтение на `')'`; лишняя закрывающая скобка в `"a)b"` может оставить хвост неразобранным и фактически превратить regex в `"a"`. Наличие двух похожих парсеров дополнительно создаёт риск расхождения интерпретатора и генератора.

**Исправление:** возвращать `Result<RegexAst, RegexError>` и требовать `pos == pattern.length()`; структурные ошибки незакрытых/лишних `(`, `)`, `[` и неверных escapes должны иметь диагностику с позицией. Вынести разбор шаблона в общую модель/IR вместо дублирования.

**Тесты:** `a)b`, `(ab`, `[abc`, `\\`, `a{`, `a{3,2}`, `a{999999999999999999}` с проверкой «ошибка компиляции DSL» вместо молчаливого принятия.

### F-06 — Regex `{m,n}` без проверки диапазона и лимита развертывания (`P1`, П)

**Место:** `src/codegen.cppm:369–406`, `:641–670`; `src/eval.cppm:455–503`.

`lo = lo * 10 + digit` и `hi = hi * 10 + digit` вычисляются в `int` без overflow check. Нет запрета `m>n`; генератор NFA далее разворачивает повторение циклом по количеству копий выражения. Огромные корректные на вид `{100000000}` могут занять память/время, а слишком длинные числа создают UB в C++ при signed overflow. При `m>n` грамматическая семантика определена неоднозначно (фактический code path строит «минимум m»).

**Исправление:** `std::from_chars`/явное checked decimal accumulation, `0 <= min <= max` либо `max=-1`, лимит на количество NFA-состояний и глубину AST/regex; ошибка типа `E_REGEX_QUANTIFIER_RANGE` с span. Собирать Thompson NFA с контролируемой сложностью, добавить resource budget компиляции.

### F-10 — Ограничители runtime молча меняют семантику (`P1`, П)

**Место:** `src/codegen.cppm:1709–1714`, `:1931–1939`, `:2159–2168`, а также код обхода prefix; сравнение: `src/eval.cppm:1233–1242`.

Генератор фиксирует `PARSLEY_MAX_MODES=64`, `PARSLEY_MAX_CTX=64`, `PARSLEY_MAX_PREFIX=64`. Когда стек режимов полон, очередной push молча игнорируется. `p_push_ctx` также молча не сохраняет 65-ю запись. Интерпретатор использует динамический `std::vector` для mode stack — **поведение интерпретатора и сгенерированного кода расходится** при достаточной вложенности.

**Исправление:** динамический стек с bounded-budget и явным `DEPTH_LIMIT`, или compile-time валидация максимальной достижимой глубины с диагностикой. Нельзя безошибочно отбрасывать семантические действия. Добавить границы 63/64/65 и повторное пополнение после backtracking.

### F-14 — Экспортируемый C ABI конфликтует при объединении нескольких парсеров (`P1`, П+У)

**Место:** `src/codegen.cppm:992–998`, генерация определений `:3039–3155`; `README.md:37–51`.

Каждая независимая генерация экспортирует `parsley_parse`, `parsley_parse_n`, `parsley_result_free`, `parsley_format_ast`, `parsley_run_examples` и общие публичные имена типов. При **статической линковке двух** разных сгенерированных библиотек в один бинарник возникают конфликты внешних имён; заголовки также конфликтуют при совместном включении в одну единицу трансляции. Динамические библиотеки с раздельным пространством символов могут работать, но использование одинакового API усложняет выбор реализации и межбиблиотечные вызовы. Реальный линк-тест не выполнялся.

**Исправление:** module-specific ABI `calc_parse_n`, `python_parse_n`, `CalcParsleyResult` либо опциональный C-префикс. Для совместимости оставить непереименованные алиасы только под явной опцией «one-parser project». Тестировать подключение двух статических библиотек/заголовков в одном C17 TU и в C++23 TU.

### F-19 — Тесты AST из генератора обрезаются до 4096 байт (`P2`, П)

**Место:** `src/codegen.cppm:3233–3242`.

Сгенерированный `parsley_run_examples()` делает `char buf[4096]`, вызывает `parsley_format_ast(&r, buf, sizeof(buf))`, а затем `strcmp` с полной ожидаемой строкой. Длинный AST гарантированно не помещается и корректный пример воспринимается как неудачный. Если форматтер сигнализирует необходимую длину, её результат здесь игнорируется.

**Исправление:** двухпроходное форматирование (`required_len` → аллокация), сравнение по длине, ограничение максимального размера с диагностикой, а не «[FAIL] expected vs truncated». Тест AST 4094, 4095, 4096, 8192 байт.

### F-20 — Полное потребление ввода требует явного `eof` (`P2`, П+У)

**Место:** `src/codegen.cppm:3040–3074`, `src/eval.cppm:1015–1026`, документация `README.md:90–95`.

Генерируемый `parsley_parse_n` возвращает `res.ok=true`, если стартовое правило вернуло значение, не проверяя `char_pos == len`/конец токенов. Пример в README сознательно использует `program = expr <* eof`. Поэтому это **не обязательно ошибка** — вероятно, контракт «parse prefix, если не указано eof»; но он рискован для вызывающих приложений, которые предполагают full parse по умолчанию.

**Рекомендация:** прямо документировать контракт и предложить `parsley_parse_complete_n()` или флаг `require_eof`. Добавить тест `"1 trailing garbage"` для обоих API и указать, где допускается partial parse.

## 5. LSP, CLI, безопасность и надёжность

### F-07 — LSP неверно переводит позиции Unicode (`P1`, П)

**Место:** `src/lexer.cppm:444–458`, `src/tooling.cppm:685–726`, `:1895–1909`.

Lexer считает столбцы по **UTF-8 codepoints** (игнорирует continuation bytes), но LSP по умолчанию использует **UTF-16 code units**. При этом `ident_at_position()` складывает переданный LSP `character` с **байтовым** смещением начала строки: `line_start + char0`. Semantic tokens в некоторых местах считают длину как количество байтов (`end_p-p`). Получаются три несовместимые системы координат, например для `é` (2 bytes, 1 codepoint, 1 UTF-16 unit) и `🙂` (4 bytes, 1 codepoint, 2 UTF-16 units).

**Влияние:** неверные hover/definition/references/diagnostic ranges и подсветка после Unicode; уязвимо к тонким off-by-n даже в простых русскоязычных комментариях.

**Исправление:** единый слой позиционного отображения `byte ↔ utf16`, LSP `positionEncoding` negotiation при поддержке UTF-8 либо корректная конвертация во всех методах. `range` + semantic token lengths обязаны соответствовать согласованной кодировке. Тесты с `é`, `漢`, emoji, surrogate pairs, CRLF, combining marks, Unicode перед именем правила и внутри строки.

### F-08 — Невалидный JSON-RPC frame может завершить LSP (`P1`, П)

**Место:** `src/tooling.cppm:2570–2605`.

Чтение `Content-Length` использует `std::stoull` без `try`/`from_chars`, без `max payload size`. Невалидное значение может бросить исключение и прекратить работу сервера; огромный размер вызывает попытку `std::string(content_length, '\0')` до чтения содержимого. Условие `content_length==0` немедленно завершает цикл.

**Исправление:** bounded protocol reader: строгое десятичное число; проверка duplicate/несогласованных headers, `content_length <= max_frame_bytes`, контроль успешного чтения/EOF, ответ JSON-RPC parse error где применимо, ограничение header lines. `std::from_chars`, `std::error_code` или явно охваченный `try`.

**Тесты:** `Content-Length: abc`, `-1`, `18446744073709551616`, `Content-Length: 100000000000`, пустой/битый JSON, несколько сообщений подряд, CRLF/LF, EOF посередине payload, лишние заголовки.

Дополнительно `src/tooling.cppm:1264–1270` молча игнорирует malformed JSON, а стандарт JSON-RPC ожидает определённые ошибки; следует провести отдельные протокольные conformance-тесты.

### F-09 — Вызов внешнего компилятора через shell-строку (`P1`, П+У)

**Место:** `src/main.cpp:98–105`, `:107–129`, `:132–173`.

`run_system_cmd` вызывает `std::system`. Команда собирается текстовой конкатенацией, а `PARSLEY_CC` и пути берутся из окружения и аргументов CLI. Оборачивание значения в `"..."` **не делает его shell-безопасным**: на POSIX подстановка команд внутри двойных кавычек работает, embedded quotes тоже нарушают границы аргумента; Windows `cmd.exe` имеет собственные метасимволы.

**Условие риска:** вредоносное значение output path, переменной окружения либо имён файлов, если ими управляет менее доверенный источник. Это **не утверждение**, что любой текст грамматики приводит к исполнению команд.

**Исправление:** запускать процесс без shell — `posix_spawn`/`execve` на POSIX, `CreateProcessW` с корректным построением аргументов на Windows; значения передавать как массив argv, не как фрагменты строки. Отдельно решить, означает ли `PARSLEY_CC` путь к бинарнику или произвольную команду с flags. Тесты с пробелами, `'`, `"`, `$()`, `&`, `;`, `%`, `!`, Unicode путями.

### F-12 — Некорректный PSL lockfile не приводит к ошибке (`P1`, П)

**Место:** `src/compiler.cppm:100–115`.

`verify_lockfile_if_present` корректно различает отсутствие файла, но при **существующем** lockfile, который нельзя прочесть либо `parse_psl_lock` вернул nullopt, тихо возвращается. Верификация схемы фактически отключается без сообщения. Это затрудняет контролируемые обновления ABI/AST, особенно в CI.

**Исправление:** отсутствие lock допускается; существующий некорректный или нечитаемый lock — диагностируемая ошибка (`E_PSL_LOCK_READ`, `E_PSL_LOCK_FORMAT`). В CI добавить тест изменения типа AST при сохранённом старом lock и тест синтаксически повреждённого lock.

### F-13 — `--fuzz` допускает отрицательные и некорректные значения (`P1`, П+Э)

**Место:** `src/main.cpp:385–401`.

Число итераций читается через `std::stoull` без проверки формата и обработчика исключений. В изолированном тесте `std::stoull("-1")` вернул `18446744073709551615`. При передаче отрицательного счётчика возможен гигантский запуск, а `--fuzz abc` приводит к необработанному исключению.

**Исправление:** `std::from_chars` по непустой строке с ASCII-цифрами (без знака), `min/max` бюджет, понятная ошибка CLI и код выхода 2. Тесты `0`, `1`, `-1`, `+1`, `abc`, `1.5`, `2^64`, `1000000000`; выбрать разумный лимит и override для длительного fuzzing.

### F-18 — Документы `.psem` могут получить устаревшую диагностику (`P2`, П)

**Место:** `src/tooling.cppm:1483–1522` и обработчики `textDocument/didOpen`, `textDocument/didChange` в `:1364–1392`.

При `update_document` семантический `.psem` сравнивается с grammar лишь тогда, когда sibling `.parsley` **уже есть** в `docs_`. Перекомпиляция `.parsley` не влечёт автоматический re-check ранее загруженного `.psem`, и обратный порядок открытия влияет на набор проверок. Это может объяснять случайные расхождения IDE-диагностики с `parsley check`.

**Исправление:** явный dependency graph URI → siblings/imports, повторная публикация diagnostics всем зависимым документам, корректная обработка `didClose`/file changes; проверка независимости от порядка открытия. End-to-end LSP sequence tests.

## 6. Алгоритмы и производительность

### F-15 — Горячий путь NFA повторно выделяет память (`P2`, П)

**Место:** `src/codegen.cppm:1567–1613`, `:1955–2017`.

`nfa_match_prefix` **на каждый вызов** аллоцирует `cur`, `nxt`, `seen`, затем освобождает. В лексере он вызывается по каждому regex-кандидату на каждой новой позиции. При `T` regex-токенах, `S` состояниях NFA, `n` байтах ввода на длинных непересекающихся/жадных шаблонах возможно до **O(T·S·n²)** работы, а количество выделений порядка количества `token × position` проверок. Это **верхняя оценка для неблагоприятного входа**, не измеренный benchmark.

**Исправление по этапам:** (1) переиспользуемый scratch-buffer на один parse, (2) лимиты шагов/состояний и профилировщик, (3) объединённый NFA с выбором token winner, (4) при реальной необходимости гибрид DFA / переходные таблицы. Сравнивать latency, allocations/token, bytes processed/s для 1 KB–10 MB и 5/20/100 токенов, включая worst cases.

### F-16 — Квадратичные операции списка и семантических строк (`P2`, П)

**Место:** `src/codegen.cppm:1410–1421`, `src/psl.cppm:4745–4753`, `:5926–5931`.

`pv_list_cons(head, tail)` создаёт новый массив и копирует весь хвост — построение списка повторными cons до длины `n` требует ~`1+2+…+n = O(n²)` копирований, если алгоритм грамматики последовательно наращивает список через cons. В PSL `psl_str_concat` копирует обе строки каждый раз, а сборка шаблонов повторными concat также имеет квадратичный сценарий.

**Исправление:** для списков — связанное представление, rope/list builder либо amortized append с финальной материализацией. Для PSL — buffer builder с capacity doubling / rope / заранее рассчитанная суммарная длина. Обязателен контроль overflow у `x.len + y.len + 1` и `count+1`.

### F-17 — В IDE используется другая regex-модель и лишняя компиляция (`P2`, П)

**Место:** `src/tooling.cppm:1815–1843`.

В token-плейграунде для каждого определения и позиции выполняется `std::regex rx(td.pattern, std::regex_constants::ECMAScript)`. Построение regex внутри inner loop дорого, а синтаксис ECMAScript и custom `RegexParser`+NFA **не обязаны совпадать** (например, классы POSIX, escape semantics и unsupported features). Получается риск, что IDE показывает токены не так, как сгенерированный parser.c.

**Исправление:** использовать одну и ту же скомпилированную regex/лексерную подсистему в интерпретаторе и IDE либо как минимум компилировать regex один раз на обновление grammar. Differential тесты на одинаковой последовательности токенов; отдельные негативные regex cases.

### F-24 — `psl_str_concat` скрывает OOM как пустую строку (`P3`, П)

**Место:** `src/psl.cppm:4745–4753`.

При `psl_arena_alloc == NULL` функция возвращает `psl_str_lit("")`; `PSL` caller не отличает «законная пустая строка» от OOM. Также `total=x.len+y.len` и `total+1` не защищены от переполнения.

**Исправление:** явный статус ошибки в runtime-контексте, tagged result или propagated `PSL_ERR_ARENA_EXHAUSTED`; лимит/string budget. Никакой silent empty fallback.

## 7. Документация, дизайн и API-контракты

### F-11 — Выбор «стратегии» не означает применение заявленного алгоритма (`P1`, П+Д)

**Место:** `src/analysis.cppm:1379–1421`, `src/codegen.cppm:2685–2824`, `:3039–3074`, `docs/Parsley — архитектура DSL для описания грамматик.md:200–245`, `AGENTS.md:70–79`.

Анализатор присваивает `selected_strategy=LL1|LLk|LALR1|PEG|GLL` в зависимости от прагмы/свойств. Однако C17 generator содержит **единый** механизм функций рекурсивного разбора с ordered choice и механизмом seed/growth для левой рекурсии. Независимых LALR action/goto tables, GLL graph-structured stack и parse forest, или Packrat-cache для **всех** правил в просмотренной ветке генератора не обнаружено. Код `analysis` выбирает **метку/диагностическую стратегию**, но не dispatch в отдельные соответствующие backend-реализации.

Это особенно важно потому, что архитектурный документ не просто перечисляет варианты: он утверждает LALR с таблицами, PEG/Packrat и GLL с лесом разборов. В README, напротив, реальный generator описан как recursive-descent + Pratt, что лучше соответствует коду.

**Решение, одно из двух:**

1. Если документ **проектный**, вверху явно указать `Design vision / Not implemented`, разделить `implemented`, `partial`, `planned`. Команда `parsley check` не должна сообщать "strategy: GLL" как гарантию фактического GLL parser runtime. Лучше `analysis mode` vs `backend parser algorithm`.
2. Если это **поддерживаемый публичный контракт**, реализовать независимые backend-ы с доказательной conformance-матрицей: LALR tables/conflicts, Packrat memo semantics, GLL ambiguity forest + API для чтения всех разборов, а не один `result.value`.

**Тест:** для грамматики с неоднозначностью проверить, что `GLL` возвращает 2 дерева; для `LALR` — наличие/использование таблиц, для `PEG` — поведение ordered choice и memoization; для каждого pragma проверить генерируемую структуру, а не только строку в диагностике.

### F-21 — Архитектурный документ описывает бэкенды за пределами фактического продукта (`P2`, Д)

**Место:** `docs/Parsley — архитектура DSL для описания грамматик.md:200–208`, `:236–259` vs `README.md:10–30`, `src/codegen.cppm`.

Проектный документ показывает backend-генерацию Haskell/Rust/TypeScript/Python, IR-сериализацию и общий conformance-прогон каждого backend-а. README подчёркивает **исключительно** C17 и не предполагает соответствующей поддержки. Это допустимо, если `docs/` — перспективный дизайн, но в текущем виде читатель может принять планы за поставляемые фичи.

**Рекомендация:** добавить `docs/STATUS.md` с матрицей `Designed / Implemented / Tested / Shipped`, даты последней проверки, ссылки на конкретные тесты и список ограничений. Обновить заголовок старого проекта до `Architecture proposal (not product specification)`.

### F-22 — Лицензирование и версионирование недостаточно однозначны (`P2`, Д)

**Место:** `README.md:482`, `editors/vscode/package.json:5–7`, `VERSION`, `scripts/bump_semver.cmake`.

README и package.json объявляют MIT, **но в ZIP не найден отдельный `LICENSE`/`COPYING` с текстом разрешения и copyright notice**. Это не означает отсутствия права на исходники, но усложняет проверку разрешённого распространения и выполнение условий MIT в сторонних сборках. Дополнительно compiler `1.3.0`, extension `1.6.0`; скрипт bump обновляет `VERSION` и `src/version.cppm`, не версию расширения. **Они могут иметь независимые циклы**, и тогда само различие версий не дефект, но нужна compatibility matrix для extension ↔ LSP ↔ compiler.

**Исправление:** включить полный `LICENSE` в исходный архив и инсталляционные пакеты; в README указать, действительно ли extension версионируется независимо и какие версии сервера поддерживает; расширить release-check на совместимость протокола.

### F-23 — Сильный старт тестов, но неполный защитный контур (`P2`, П)

**Место:** `CMakeLists.txt:36–78`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `tests/test_main.cpp:900–954`.

**Важно отметить существующие тесты:** `Calc`, `Python`, `Swift`, `Kotlin`, `Haskell`, `Mini`, `LexModes`, `HtmlContext`, PSL tests и C17 integration checks; CI имеет 3-платформенную матрицу. Это не «отсутствие тестов». Проблема — их фокус: тесты расширения в `tests/test_main.cpp` проверяют наличие файлов/JSON/JS-синтаксис, а не реальное поведение LSP/extension; `--fuzz 30/50` грамматически генерирует преимущественно позитивные примеры; не обнаружена обязательная матрица отказов аллокатора, Unicode-позиций, SQL-like adversarial inputs, невалидных regex и differential testing interpreter ↔ C17.

**Рекомендация:** отдельные suites `conformance`, `fault-injection`, `differential`, `lsp-protocol`, `perf-regression`, sanitizer Debug CI. При наличии выполнимого toolchain ставить baseline по времени/памяти с порогами и шумозащитой (например, не блокировать каждую PR на нестабильном microbenchmark).

## 8. Матрица граничных случаев: что добавить в тесты

| Подсистема | Вход/состояние | Проверяемый инвариант |
|---|---|---|
| C-literal emitter | Соседние байты `01 41`, `00 37`, `FF 46`, полный диапазон `[0,255]` | Сохранить `len` и байты после компиляции. |
| Числа | `±2^53`, `INT64_MIN/MAX`, переполнение `strtoll`, `NaN/Inf` | Нет потери `Int`, range errors явны. |
| Размеры | `SIZE_MAX` длина, `len=0`, `input=NULL`, буфер нулевой длины | Нет умножения с overflow, нет чтения вне памяти. |
| Regex | Лишние `)`, открытые `(`, пустые группы, `[]`, гигантские `{m,n}` | Полное потребление паттерна и ограничение ресурса. |
| NFA | `a?`, `(a?)*`, глубокая вложенность, длинный нематч | Нет бесконечного цикла, ограничены время/память. |
| Lexer | Keyword vs identifier, одинаковые длины, несколько modes | Maximal munch + precedence + stable tie-breaking. |
| Context | 63/64/65 bindings, backtracking после push/pop | Нет silent drop; паритет C17/eval. |
| Parse API | Успешный префикс + мусорный суффикс | Ясный контракт full vs partial. |
| AST | 4095/4096/8192 символов, миллионы list items, пустая структура | Нет silent truncation и O(n²) в горячем пути. |
| OOM | Отказ 1-й, 2-й, n-й аллокации, `realloc` failure | Ошибка/cleanup вместо crash/corrupted AST. |
| LSP | `é`, `漢`, `🙂` перед идентификатором, CRLF | Корректные UTF-16 ranges и semantic tokens. |
| JSON-RPC | Некорректные Content-Length/JSON, oversized frame, EOF | Server не падает и не аллоцирует неограниченно. |
| Workspace | Сначала `.psem`, потом `.parsley`; изменение sibling, закрытие | Диагностика соответствует текущему состоянию файлов. |
| CLI | `--fuzz -1/abc/huge`, вывод в пути с shell-метасимволами | Контролируемая ошибка; никаких shell injections. |
| Packaging | 2 независимых C17 парсера в 1 exe; стат./динамич. | Нет конфликтов ABI/symbols; независимый namespace. |
| CI | Fault injection + ASan/UBSan + Windows CRT + macOS ARM | Дефекты краевых случаев обнаруживаются до релиза. |

## 9. Предлагаемая архитектура для исправления корневых причин

### 9.1. Общий semantic core между интерпретатором и C17

Сейчас интерпретатор (`src/eval.cppm`) и backend (`src/codegen.cppm`) независимо реализуют regex-разбор, NFA, lexer semantics и частично context handling. Чем больше независимого кода, тем выше риск «`parsley test` прошёл, сгенерированный C17 ведёт себя иначе».

Предлагается **единая исполнимая спецификация** на уровне IR:

```text
DSL source
  ↓
Parsed AST → Typed IR → Normalized Grammar IR
                          ├── prevalidated regex automata + token precedence
                          ├── explicit error/result contract
                          ├── context / mode stack semantics
                          └── fixed interpretation of parse strategy
                                   ├── reference evaluator
                                   └── C17 generator
                                          ↓
                            Same golden conformance vectors
```

Это не обязательно означает разделение одной исходной C++ библиотеки с генерируемым C17 — C17 должен оставаться standalone. Достаточно **генерировать из одного нормализованного автомата и контрактных таблиц** и валидировать идентичный результат на детерминированном differential-suite.

### 9.2. Безопасная модель памяти для публичного C17

Предлагаемая цепочка:

1. `ParsleyParser` владеет arena/scratch с лимитом памяти.
2. `checked_alloc(size,count)` возвращает либо память, либо структурированный `PARSLEY_ERR_OOM`.
3. Все constructors и `pv_clone` возвращают checked result, а не nullable pointer с последующим dereference.
4. `ParsleyResult` содержит статус ошибки и гарантированно освобождаемое состояние даже при partial parse.
5. Пределы `MAX_CTX/MODES/PREFIX` либо документированы как проверяемые ошибки, либо заменены на динамические контейнеры.
6. Никакой обязательной зависимости от сборщика мусора или C++ runtime не требуется.

### 9.3. Формализовать контракты

Минимально необходимы текстовые спецификации:

- Lexer: exact maximal-munch comparator, skips, tie-breaking, lexical modes, Unicode/bytes.
- Regex subset: поддерживаемые классы/escape/syntax, error semantics и resource limits.
- Parser API: consumption contract, expected errors, ownership/free, null/empty input, ABI namespace.
- Strategy: что реально **меняется в generated runtime** для LL1/LLk/LALR/PEG/GLL.
- PSL lock: когда обязателен, как ведёт себя повреждённый файл.
- LSP: position encoding, supported methods, incremental change/close behaviour.
- Совместимость: versions compiler / generated runtime ABI / VS Code extension.

## 12. Минимальные «шаги воспроизведения» для следующих проверок

**A. C escape — воспроизведено локально:**

```bash
cat > escape.c <<'C'
#include <stdio.h>
int main(void) {
  const unsigned char s[] = "\x01A";
  printf("sizeof=%zu first=%02x\n", sizeof s, s[0]);
}
C
cc -std=c17 escape.c -o escape && ./escape
# observed: sizeof=2 first=1a
# expected two data bytes: sizeof=3 first=01, second=41
```

**B. Числа и `--fuzz -1` — изолированное доказательство:**

```cpp
#include <cstdint>
#include <string>
#include <iostream>
int main() {
  std::cout << std::stoull("-1") << '\n';
  constexpr std::int64_t n = 9007199254740993LL;
  std::cout << static_cast<std::int64_t>(static_cast<double>(n)) << '\n';
}
// observed: 18446744073709551615; 9007199254740992
```

**C. Контекстный maximal munch — кандидат на e2e regression:** объявить `keyword "if"` и `identifier /[a-z]+/`, использовать грамматику `context do`, подать `"iffy"`. Сравнить `parsley test` и `parser.c` в scannerless/normal grammar; зафиксировать лексический winner и остаток ввода. **Не отмечать как пройденный тест без компилятора.**

**D. Линковка двух парсеров — кандидат:** сгенерировать `Calc/parser.c` и `Mini/parser.c`, собрать оба статических архива, подключить обе реализации к одному C17 executable и проверить linker errors/символы. **Не выполнялось в текущей среде.**

**E. Проверка полного runtime после получения toolchain:**

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_C_COMPILER=clang-23 \
  -DCMAKE_CXX_COMPILER=clang++-23 \
  -DCMAKE_BUILD_TYPE=Debug \
  -DPARSLEY_BUILD_TESTS=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
# Затем отдельные sanitizer/fault-injection/differential suites.
```

Инструментарий команды выше следует синхронизировать с фактически доступными Clang/CMake и поддержкой C++26 modules на выбранной платформе. Без этого не стоит интерпретировать конфигурационную ошибку как качество кода.

## 13. Вопросы, которые следует решить перед production-поддержкой

1. **Каков формальный смысл pragma `MODE`?** Это реально гарантия разных parser engines или только стратегия предупреждений/анализа? Что именно должен выдавать GLL при нескольких разборах?
2. **Существует ли нулевой по умолчанию ресурсный бюджет?** Максимальные длины input/regex, глубина AST, количество NFA-состояний, память на parse.
3. **Можно ли использовать два генерированных парсера в одном процессе** (и особенно в одном статически собранном binary)?
4. **Префиксный разбор — намеренная семантика публичного `parsley_parse`?** Если да, где специфицирована необходимость `eof`?
5. **Является ли PSL lock обязательным контрактом при его присутствии?** Должен ли битый lock блокировать сборку?
6. **Версии расширения и компилятора независимы?** Как гарантируется совместимость методов LSP (`parsley/*`) и semantic tokens?
7. **Какие performance claims уже измерены?** Нужны reproducible benchmarks, hardware/build flags, размер входа, сравнение с ANTLR4 с эквивалентными grammars и identical parsing semantics.
8. **Допускаются ли недоверенные грамматики/исходные файлы?** От этого зависит приоритет sandboxing, shell removal и CPU/memory budgets.

## 14. Вывод

Parsley технически интересен именно потому, что уже интегрирует несколько тяжёлых подсистем: собственный DSL, статический анализ, генерацию standalone C17, PSL и IDE. Наличие матричного CI и настоящих фикстур — весомый плюс. Но **качество production parser generator определяется не количеством поддержанных грамматик, а сохранением инвариантов на граничных входах**: байты не должны меняться при генерации C, `Int64` не должен терять точность, некорректный regex не должен молча упрощаться, недостаток памяти не должен превращаться в аварийное завершение, а поведение интерпретатора и компилируемого парсера должно быть одним и тем же.

Наиболее полезная следующая инженерная инвестиция — **исправить F-01/F-02/F-03 и закрепить эти случаи differential/golden/fault-injection тестами**. Параллельно нужно честно синхронизировать обещания LL/LALR/PEG/GLL и мульти-backend архитектуры с существующей реализацией. После этого оптимизация NFA, PSL и работа над LSP будут опираться на проверяемый семантический фундамент.

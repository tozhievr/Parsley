# PSL — архитектура семантического слоя Parsley

Статус: черновик v0.2 · Дополняет документ «Parsley — архитектура DSL для описания грамматик». Семантика описывается на самом Parsley (модуль semantics), компилируется в C17 и входит в состав сгенерированного фронтенда.

## 1. Назначение и границы

Семантика языка описывается на самом Parsley: модуль `semantics Calc where` лежит в файле `Calc.psem` рядом с грамматикой `Calc.parsley` и компилируется в C17 вместе с ней. Он задаёт статическую семантику: области видимости, символы, типы, проверки корректности и правила линтинга. Результат входит в состав фронтенда как его middle-end, отдельного артефакта нет.

LLM один раз читает референсы и мануалы языка и пишет такой модуль. Это обычный текст на Haskell-подобном DSL, а не код на C: детерминированный компилятор проверяет его и переводит в C17. Всё, что нельзя проверить машинно, сопровождается источником, статусом и уровнем уверенности.

Вне границ: динамическая семантика (исполнение), оптимизации, кодогенерация целевого языка. Анализ потока данных (CFG, определённые присваивания, недостижимый код) описывается блоком flow, многофайловые проекты — декларацией project, а вывод типов опирается на унификацию Хиндли–Милнера.

## 2. Как семантика не засоряет язык

Грамматика ничего не знает о семантике, а семантика не может повлиять на разбор. Общее у них только ядро языка: паттерны, выражения, импорты, прагмы и layout. Всё остальное принадлежит одному из двух видов модуля.

| Конструкция | Модуль `grammar` | Модуль `semantics` |
| --- | --- | --- |
| `token`, `skip`, `mode`, `keywords` | да | нет |
| правила, `operators`, `context` | да | нет |
| `data` (AST) | да | нет, только импорт |
| `type`, `tycon`, `kind`, `builtin`, `node`, `flow`, `analysis`, `lint`, `diag`, `profile`, `project`, `example` | нет | да |
| выражения, паттерны, `import`, прагмы | общее ядро | общее ядро |

Гарантии, которые не дают словарю языка разрастаться:

- **Словарь определяется заголовком модуля.** Ключевое слово `lint` в модуле грамматики — обычная синтаксическая ошибка, а не особый случай.
- **Ключевые слова семантики контекстные.** Они действуют только внутри `semantics`, поэтому не резервируют имена в грамматиках: правило можно назвать `lint` или `node`.
- **Один парсер и один форматтер** на оба вида модулей; набор конструкций переключается по заголовку.
- **Зависимость односторонняя.** Семантика импортирует грамматику (`import Calc`), обратный импорт запрещён.

## 3. Принципы

1. **Один язык паттернов.** Узлы AST адресуются теми же конструкторами `data`, что и в грамматике: `Let x e body`, `Bin Div _ r`.
2. **Выражения тотальны.** Нет пользовательской рекурсии и циклов, время вычисления ограничено размером поддерева. Это гарантия для сгенерированного C17.
3. **Эффекты видны в типах.** Блоки `node` пишутся в монаде `Sem` с фиксированным набором эффектов (`declare`, `lookup`, `scope`, `require`). По ним компилятор планирует проходы.
4. **Правило самоаттестуется.** Каждый `lint` обязан иметь `example`; компилятор их исполняет.
5. **Происхождение — часть данных.** Прагмы `SOURCE`, `STATUS`, `CONFIDENCE` лежат прямо у правила.
6. **Никаких внешних форматов.** Один синтаксис, один форматтер, диффы построчные.
7. **Ошибка в семантике не ломает разбор.** Фронтенд собирается и без семантического модуля.

## 4. Синтаксис семантического модуля

Модуль семантики для языка Calc из основного документа (арифметика с `let`, функциями и встроенными константами):

```haskell
semantics Calc where

import Calc                      -- AST и токены грамматики
import Parsley.Sem.Prelude

source ref = manual "Calc Language Reference" rev "2.1"

-- Типы и символы -------------------------------------------
type Number = Double

kind Variable where shadowing = Warn
kind Function

builtin sin :: Function (Number -> Number)            {-# SOURCE ref "4.2" #-}
builtin max :: Function (Number -> Number -> Number)  {-# SOURCE ref "4.3" #-}
builtin pi  :: Variable Number                        {-# SOURCE ref "4.1" #-}

-- Диагностики ----------------------------------------------
diag E001 :: Error "Undefined variable `{name}`"
diag E002 :: Error "Undefined function `{name}`"
diag E003 :: Error "`{name}` expects {expected} argument(s), got {actual}"
diag E004 :: Error "Operand must be a Number"

-- Уравнения по узлам AST -----------------------------------
node Num _ where
  type = Number

node Var x where
  sym  <- lookup Variable x `orFail` E001 { name = x }
  type =  typeOf sym

node Call f args where
  fn <- lookup Function f `orFail` E002 { name = f }
  require (length args == arity fn)
    `orFail` E003 { name = f, expected = arity fn, actual = length args }
  require (and [typeOf a == Number | a <- args]) `orFail` E004
  type = Number

node Let x e body where
  scope body $ declare Variable x (typeOf e)
  type = typeOf body

node Bin _ l r where
  require (typeOf l == Number && typeOf r == Number) `orFail` E004
  type = Number

-- Линтинг --------------------------------------------------
{-# SOURCE ref "2.4"; STATUS reviewed; CONFIDENCE 0.95 #-}
lint unusedBinding :: Warning, Style
  match (Let x _ _)
  when  useCount x == 0 && not ("_" `isPrefixOf` x)
  say   "Variable `{x}` is never used"
  fix   "Prefix with underscore" Safe (replace (nameSpan x) ("_" <> x))

example unusedBinding
  fires  "let x = 1 in 2"
  silent "let x = 1 in x + 1"
  silent "let _x = 1 in 2"

{-# SOURCE ref "3.1"; STATUS verified #-}
lint divisionByZero :: Error, Correctness
  match (Bin Div _ r)
  when  constFold r == Just 0
  say   "Division by zero"

example divisionByZero
  fires  "1 / (2 - 2)"
  silent "1 / 2"

profile recommended = [unusedBinding, divisionByZero]
```

**Объявления модуля**

| Объявление | Назначение |
| --- | --- |
| `semantics M where` | Заголовок модуля; `import G` подключает грамматику |
| `source` | Источник знаний: мануал, стандарт, раздел |
| `type`, `tycon`, `kind` | Синонимы типов, конструкторы типов с параметрами и виды символов с их свойствами |
| `builtin` | Предопределённые символы с сигнатурами, в том числе полиморфными |
| `node P where` | Уравнения для конструктора AST: области, разрешение имён, ограничения типов, проверки |
| `flow P = ...` | Рёбра управляющего графа для конструктора AST |
| `analysis` | Анализ потока данных в форме gen/kill |
| `lint` | Правило линтинга: `match`, `when`, `say`, `fix` |
| `diag` | Каталог диагностик: код, severity, шаблон сообщения |
| `example` | Положительные (`fires`) и отрицательные (`silent`) примеры |
| `profile` | Наборы правил (`recommended`, `strict`) |
| `project where` | Единицы компиляции, импорты, экспорты, видимость |
| Прагмы | `SOURCE`, `STATUS`, `CONFIDENCE`, `LOCKED` |

**Привязка к грамматике.** Паттерн `Let x e body` проверяется по `data Expr` из импортированной грамматики: существование конструктора, арность, типы связанных переменных. Вложенные паттерны (`Bin Div _ r`) работают так же, как в обычном Haskell.

**Язык выражений** — подмножество того же языка, что и в грамматике:

- Типы: `Bool`, `Int`, `Text`, `Maybe a`, `[a]`, `Node`, `Symbol`, `Type`, `Span`.
- Операторы: `==`, `/=`, `<`, `<=`, `&&`, `||`, `not`, `+`, `-`, `*`, `<>`, `if/then/else`, `case`, охранные выражения.
- Списки: генераторы `[f a | a <- xs, p a]` и свёртки `any`, `all`, `and`, `count` по спискам и поддеревьям.
- Встроенные запросы: `typeOf`, `lookup`, `arity`, `useCount`, `parent`, `ancestors`, `enclosing`, `constFold`, `nameSpan`, `isSubtype`.
- Ограничения: нет ввода-вывода, пользовательской рекурсии и аллокаций вне арены; глубина выражения не больше 64.

## 5. Модель вычисления

Семантический модуль — атрибутная грамматика плюс запросы. Блок `node` пишется в монаде `Sem`: `type =` задаёт синтезируемый атрибут, `scope` и `declare` — наследуемые, `lookup` разрешает имя, а ``require cond `orFail` E`` порождает диагностику. Выбор эффектов не зависит от вычисленных значений (только охранные выражения), поэтому компилятор видит граф зависимостей статически и планирует пять проходов по AST:

1. **Сбор объявлений:** `declare`, `scope`.
2. **Разрешение имён:** `lookup`.
3. **Вывод типов:** ограничения из `type` и `unify`, унификация, затем `require`.
4. **Поток данных:** построение CFG по `flow`, решение `analysis`.
5. **Линтинг:** все `lint`, объединённые в один обход с диспетчеризацией по тегу конструктора.

Циклическая зависимость атрибутов — ошибка компиляции семантики с указанием цикла. Линты независимы друг от друга и читают уже вычисленные атрибуты.

## 6. Система типов: унификация Хиндли–Милнера

Типы выводятся унификацией Хиндли–Милнера: блоки `node` только порождают ограничения, а решает их компилятор. Это даёт let-полиморфизм, дженерики целевых языков и вывод типов без аннотаций.

```haskell
tycon Number
tycon List a
tycon Fn a b

builtin map :: forall a b. Function ((a -> b) -> List a -> List b)
builtin len :: forall a.   Function (List a -> Number)

node Lam x body where
  a <- fresh                                -- свежая переменная типа
  scope body $ declare Variable x (mono a)
  type = Fn a (typeOf body)

node App f arg where
  r <- fresh
  unify (typeOf f) (Fn (typeOf arg) r)
    `orFail` E010 { expected = typeOf f, actual = typeOf arg }
  type = r

node LetIn x e body where                   -- let-полиморфизм
  scope body $ declare Variable x (generalize (typeOf e))
  type = typeOf body
```

**Эффекты вывода типов**

| Эффект | Смысл |
| --- | --- |
| `fresh` | Свежая переменная типа текущего уровня |
| `unify a b` | Ограничение `a ~ b`; при неудаче срабатывает `orFail` |
| `mono t` | Монотип без обобщения (параметры лямбд) |
| `generalize t` | Обобщение переменных, чей уровень глубже текущего |
| `lookup` полиморфного символа | Неявная инстанциация со свежими переменными |

**Алгоритм.** Algorithm J с уровнями для обобщения, union-find для переменных типов и occurs check. При неудаче унификации затронутые переменные получают специальный тип `Error`, а каскадные диагностики подавляются. Порядок сообщений фиксирован порядком обхода AST.

**Границы первой версии.** Чистый Хиндли–Милнер не покрывает подтипизацию, перегрузку и типы высших рангов. Для языков, которым они нужны, предусмотрены декларация `coerce` (неявные приведения, применяются как запасной вариант при неудаче `unify`) и `overload` (выбор по типам аргументов после разрешения имён). Всё остальное вне рамок v1.

## 7. Анализ потока данных: блок flow

Блок `flow` описывает управляющий граф языка, а `analysis` — анализы над ним в форме gen/kill. Построение CFG и решатели генерирует компилятор. Пример для императивного языка Mini с `if`, `while` и `return`:

```haskell
semantics Mini where
import Mini

-- Управляющий граф: по одному уравнению на конструктор AST
flow Block ss      = chain ss
flow If c t e      = branch c [t, e]
flow While c body  = loop c body
flow Return e      = jump e Exit
flow Break         = jumpOut (enclosing While)
flow Continue      = jumpTo  (enclosing While)

-- Анализы: направление, вид, домен и gen/kill
analysis assigned :: Forward, Must Symbol
  gen  (Assign x _)       = [x]
  gen  (Decl x (Just _))  = [x]

analysis live :: Backward, May Symbol
  gen  (Var x)            = [x]
  kill (Assign x _)       = [x]

-- Линты поверх графа
lint useBeforeAssign :: Error, Correctness
  match (Var x)
  when  x `notMember` before assigned
  say   "`{x}` may be used before it is assigned"

lint unreachableCode :: Warning
  match (s :: Stmt)
  when  not (reachable s)
  say   "Unreachable code"

lint deadStore :: Warning, Style
  match (Assign x _)
  when  x `notMember` after live
  say   "Value assigned to `{x}` is never read"
```

**Правила блока**

- Уравнение `flow` собирается из комбинаторов `chain`, `branch`, `loop`, `jump`, `jumpOut`, `jumpTo`. Узлы без уравнения линейны: потомки выполняются слева направо.
- У `analysis` есть направление (`Forward` или `Backward`) и вид: `Must` — свойство на всех путях (пересечение), `May` — хотя бы на одном пути (объединение).
- Передаточная функция пишется только как `gen` и `kill`. Такая форма монотонна по построению, поэтому итеративный решатель всегда сходится, а в C17 всё сводится к битовым векторам.
- Запросы в линтах: `before a n`, `after a n` (факты анализа `a` до и после узла), `reachable n`, `dominates m n`.
- Паттерн `(s :: Stmt)` выбирает любой узел типа `Stmt`.

**Границы первой версии:** анализ внутри одной процедуры, без указателей и алиасинга, только битовые домены (достигающие определения, живые переменные, определённое присваивание). Исключения и `goto` выражаются через `jump`. Интервальные и другие нераспределительные домены вне рамок v1.

## 8. Проекты: декларация project

Декларация `project` описывает, как единицы компиляции складываются в программу: что считается модулем, как разрешаются импорты и что видно снаружи.

```haskell
semantics Mini where
import Mini

project where
  unit     Module                          -- единица компиляции: файл с корнем Module
  imports  (Import path names) = unit (resolve path)
  exports  (Export names)      = publish names
  prelude  = "std/prelude"
  search   = [".", "lib"]
  cycles   = Forbidden                     -- или Allowed
```

**Правила**

- **Идентичность символа** — пара `unit::name`. `lookup` ищет по областям, затем по экспортам импортированных единиц, затем в `prelude`.
- **Порядок анализа.** Единицы обрабатываются в топологическом порядке графа импортов. Для каждой строится интерфейс (экспортируемые символы и их типы); зависимые единицы используют его без повторного разбора, поэтому анализ инкрементален.
- **Циклы.** При `Forbidden` выдаётся диагностика с цепочкой импортов; при `Allowed` компоненты сильной связности анализируются совместно одним запуском унификации.
- **Нет ввода-вывода во фронтенде.** Хост передаёт функцию чтения файлов, а фронтенд запрашивает единицы по мере разрешения импортов.

```c
typedef int (*psl_fetch)(void *user, psl_str path, psl_str *src);

mini_project *mini_project_new(psl_arena *arena, psl_fetch fetch, void *user);
int           mini_project_add(mini_project *pr, psl_str path);   /* точка входа */
int           mini_project_analyze(mini_project *pr, psl_sink sink, void *user);
```

**Границы первой версии:** условная компиляция и макросы (препроцессор целевого языка) не описываются, управление пакетами и версиями зависимостей остаётся на стороне хоста.

## 9. Конвейер получения семантики

1. **Вход для LLM:** справка по Parsley и по модулю `semantics` (его грамматика сама написана на Parsley), каталог AST-типов из IR грамматики, список токенов, два-три эталонных модуля и фрагменты мануала с идентификаторами разделов.
2. **Генерация:** модель выдаёт только текст `.psem`.
3. **Проверки компилятора:** разбор, разрешение имён, типизация, привязка паттернов к AST, планирование атрибутов.
4. **Примеры:** запуск всех `example` на сгенерированном анализаторе.
5. **Согласованность:** противоречия, мёртвые правила, пересекающиеся `match`.
6. **Ревью человеком:** построчный diff, повышение `STATUS`.
7. **Компиляция в C17:** семантика становится частью фронтенда.

Диагностики шагов 3–5 возвращаются модели в машинном виде (JSON) вместе с предложенными исправлениями, цикл ограничен N итерациями. Чтобы новый DSL не мешал модели, семантический профиль языка строго регулярен: у каждой декларации фиксированная форма, а `parsley fmt` приводит вывод модели к канону, так что диффы стабильны.

**Статусы правил** задаются прагмой `STATUS`: `draft` (компилируется, но severity ограничена `Warning`), `reviewed` (прочитано человеком), `verified` (подтверждено корпусом или эталонной реализацией). Сборка для production запускается с `--min-status reviewed`.

## 10. Компиляция в C17

**Результат компиляции фронтенда**

| Файл | Содержимое |
| --- | --- |
| `calc_ast.h` | Тегированные объединения для `data`, `Span`, интернированные строки |
| `calc_parse.h/.c` | Лексер и парсер из грамматики |
| `calc_sem.h/.c` | Всё, что сгенерировано из `Calc.psem` |
| `calc_diag.h` | Каталог кодов диагностик |

**Соответствие конструкций семантики и C17**

| Конструкция | Генерируемый код |
| --- | --- |
| `node` | Ветка `switch (n->tag)` в соответствующем проходе |
| `scope` / `declare` | Стек областей и хеш-таблица с открытой адресацией по интернированным именам |
| `type`, `unify` | Типы hash-consed в арене; переменные типов — union-find, унификация без рекурсии и без аллокаций вне арены |
| `flow`, `analysis` | CFG из массивов блоков и рёбер в арене; gen/kill как битовые векторы `uint64_t`, итеративный решатель с рабочим списком |
| `project` | Структура `psl_project`: единицы, граф импортов, интерфейсы модулей; чтение файлов делегируется хосту через `psl_fetch` |
| `lint` | `static void lint_<name>(...)`, запись в таблице диспетчеризации по тегу |
| `diag` | `static const psl_diag_def` с шаблоном и типами аргументов |
| `profile` | Битовая маска включённых линтов |
| `example` | Сгенерированный `calc_psl_selftest()` |

**Требования к сгенерированному коду**

- Строгий C17: `-std=c17 -pedantic`, без расширений GNU, без VLA.
- Без `malloc`: вся память берётся из арены `psl_arena`, которую передаёт вызывающий код. Глобального состояния нет, код реентерабельный.
- Нет неопределённого поведения: `constFold` использует проверяемую арифметику, глубина обходов ограничена.
- Инварианты таблиц проверяются через `_Static_assert`.
- Стабильный ABI: публичные структуры содержат поле `size`, версия схемы вшита в заголовок.
- Опционально freestanding: из стандартной библиотеки нужны только `<stddef.h>`, `<stdint.h>`, `<string.h>`.

**Публичный API**

```c
typedef struct calc_ctx calc_ctx;
typedef void (*psl_sink)(void *user, const psl_diag *d);
```

**Пример сгенерированного кода для `unusedBinding`**

```c
/* generated from lint unusedBinding; do not edit */
static void lint_unusedBinding(calc_ctx *cx, const Expr *n) {
    const psl_str x = n->as.let.name;
    if (psl_use_count(cx, n) == 0 && !psl_starts_with(x, psl_lit("_"))) {
        psl_diag d = psl_diag_new(&CALC_LINT_unusedBinding, n->span);
        psl_diag_arg_text(&d, "x", x);
        psl_diag_fix_replace(&d, psl_name_span(cx, n),
                             psl_concat(cx, psl_lit("_"), x), PSL_FIX_SAFE);
        psl_emit(cx, &d);
    }
}

static void run_lints(calc_ctx *cx, const Expr *n) {
    switch (n->tag) {
        case EXPR_LET: lint_unusedBinding(cx, n); break;
        case EXPR_BIN: lint_divisionByZero(cx, n); break;
        default: break;
    }
}
```

**Соответствие типов `data` и C17:** `Text` → `psl_str` (указатель и длина, UTF-8), `[a]` → срез в арене, `Maybe a` → указатель, допускающий `NULL`, ADT → `struct` с `tag` и `union`.

## 11. Доверие к выводу LLM

Модель считается ненадёжным источником. Компилятор защищается так:

- **Обязательные примеры.** Линт без `fires` и `silent` отклоняется.
- **Мутационная проверка.** Компилятор мутирует пример с `fires`; после «починки» правило обязано перестать срабатывать.
- **Проверка цитат.** При наличии исходных текстов прагма `SOURCE` содержит локатор раздела и хеш нормализованной выдержки; несуществующая цитата понижает статус до `draft`.
- **Поиск противоречий.** Правила с пересекающимся `match` и взаимоисключающими выводами помечаются, неизвестные встроенные символы тоже.
- **Лимиты.** Размер модуля, число правил, глубина выражений; тотальность выражений гарантируется типами.
- **Человеческое ревью.** Diff по строкам; правило с прагмой `LOCKED` модель перезаписать не может.

## 12. Эволюция и версионирование

- Имена правил (`unusedBinding`) стабильны. При перегенерации модули сливаются по имени, переименование фиксируется прагмой `SUPERSEDES`.
- Компилятор записывает хеш AST-типов грамматики в lock-файл `Calc.psem.lock`. Изменение грамматики ломает сборку семантики и сообщает, какие паттерны устарели; модели передаётся diff типов для перегенерации.
- Версия языка семантики фиксируется в заголовке (`{-# LANGUAGE Sem1 #-}`), компилятор принимает текущую и предыдущую мажорные версии.

## 13. Связь с основным документом

**Изменение к документу по Parsley.** Основной бэкенд — **C17**, а не Haskell: фронтенд на C17 является базовым требованием. Haskell-бэкенд остаётся вторичным, эталонным для конформанс-тестов. MVP включает C17-бэкенд, парсер, `data` → tagged unions и семантику без `context`.

Семантический модуль использует тот же IR, что и бэкенды Parsley: типы AST берутся из `gTypes`, паттерны проверяются при привязке к грамматике, диагностики разделяют инфраструктуру (`Span`, коды, шаблоны) с ошибками разбора. В конвейер добавляется стадия `Sem`: после анализа грамматики компилятор разбирает `*.psem`, строит Sem IR и отдаёт его C17-бэкенду вместе с Grammar IR. Название PSL (Parsley Semantic Layer) относится к этой подсистеме; префикс `psl_` носит её runtime-библиотека.

## 1. Резюме

Проект амбициозный и в целом аккуратно структурирован: чёткий конвейер (lexer → parser → resolve → typecheck → desugar → analysis → codegen), диагностики со span'ами, Thompson-NFA вместо backtracking-регулярок (нет ReDoS в классическом смысле), seed-growing для левой рекурсии, самотесты прямо в грамматике. Для версии 1.3.0 объём сделанного впечатляет.

Основные проблемы собираются в **пять тем**:

1. **«Тихие» ошибки вместо диагностик.** Регекс-диалект принимает неподдерживаемые конструкции (`^`, `$`, `\b`, `(?=…)`, `\x41`, ленивые кванторы) и молча превращает их в литералы или игнорирует. Аналогично — жёсткие лимиты в рантайме (64 режима/префикса/контекста), неверный `START`, переполнение чисел в парсере. Для генератора парсеров это худший класс дефектов: сгенерированный парсер «работает», но разбирает не то, что описано.
2. **Генератор C-кода производит некорректный C в реальных случаях** (✅ `\x`-эскейпы, триграфы), рантайм не проверяет `malloc`, не ограничивает глубину рекурсии, зависит от локали (`strtod`).
3. **Документация обещает больше, чем реализовано**: `MODE LL1|LLk|LALR|PEG|GLL` не меняет сгенерированный код (только комментарий), «Complete» грамматики — подмножества, «zero unchecked malloc» — неверно, README не описывает часть CLI, `docs/` описывает несуществующие бэкенды.
4. **Хрупкость инструментов**: нет `try/catch` в `main` и в LSP (`std::stoull` на мусоре → `terminate`), запуск компилятора C через `std::system` со склейкой строк, захардкоженный `D:/clang-23.1.3`.
5. **Производительность**: NFA-симуляция делает 3 аллокации *на каждый вызов* (а вызывается на каждую позицию × каждый токен), нет мемоизации, анализ FIRST/FOLLOW копирует `std::set<std::string>` в цикле.

## 2. Критические находки

### C-01 🔴 ✅📖 Генератор C-строк портит литералы (`\x`-эскейпы и триграфы)

**Где:** `src/codegen.cppm:162–198`, функция `c_string_lit`.

**Проблема.** Для байтов `< 0x20` и `≥ 0x7f` функция печатает `\xNN`. В C шестнадцатеричный эскейп `\x` **поглощает все следующие hex-цифры**, поэтому если за таким байтом идёт символ `0–9a–fA–F`, получается один эскейп с огромным значением.

**Воспроизведено** (`gcc -std=c17 -Wall -Wextra -pedantic`, строка «т1» в UTF-8 = `D1 82 '1'`, т.е. то, что генерирует `c_string_lit`):

```c
const char* s = "\xd1\x821";   /* ожидалась длина 3 */
/* warning: hex escape sequence out of range;  strlen(s) == 2 */
```

GCC только предупреждает и усекает; Clang (основной компилятор проекта) даёт **ошибку** → `parsley build` падает на «сборке shared-библиотеки», хотя грамматика корректна.

**Когда срабатывает:** любое имя `example`, строка-литерал в грамматике или входной пример, где non-ASCII/управляющий символ стоит перед `[0-9a-fA-F]`: `example "тест1"`, `"é1"`, токен `"№1"`. Фикстуры не ловят дефект только потому, что их non-ASCII имена состоят из одних кириллических букв (после каждого `\xNN` идёт `\`).

**Вторая проблема в той же функции — триграфы.** Проект собирается с `-std=c17` (строгий ISO), где триграфы включены:

```c
const char* t = "??(";   /* → "[" ; warning: trigraph ??( converted to [ */
```

Затрагивает строки вида `"??("`, `"??)"`, `"??="`, `"??/"` и т.д. (операторы `??`, `?:` в Swift/Kotlin рядом со скобками, регулярки с `??`).

**Исправление:**

```cpp
default:
  if (c < 0x20 || c >= 0x7f) {
    // Всегда ровно 3 восьмеричные цифры — эскейп завершается однозначно.
    out << '\\' << char('0' + ((c >> 6) & 7)) << char('0' + ((c >> 3) & 7)) << char('0' + (c & 7));
  } else if (c == '?') {
    out << "\\?";            // блокирует триграфы
  } else {
    out << char(c);
  }
```

(Заодно: `case '\0'` → `"\\0"` тоже подвержен проблеме — `"\0"` + `'1'` даёт `\01`; используйте `\000`.) Добавьте тест: `example "тест1"` и `"a\x01b"` в фикстурах + компиляция с `-Werror`.

### C-02 🔴 📖 Регулярные выражения: неподдерживаемое молча меняет смысл

**Где:** `src/codegen.cppm:292–575` (`RegexParser`), копия в `src/eval.cppm:384+`.

Парсер не валидирует вход и «проглатывает» всё неизвестное:

| Конструкция | Что происходит на самом деле | Ожидание автора |
|---|---|---|
| `^`, `$` | литеральные символы `^` и `$` (`parse_atom`, ветка `default`) | якоря |
| `\b`, `\B` | литералы `b`, `B` (`add_escape_to_matcher`, `default`) | граница слова |
| `(?=x)`, `(?!x)`, `(?<n>x)` | обрабатывается только `(?:`; для `(?=` символ `?` становится литералом (стр. 543) | lookahead / именованная группа |
| `\1` (backreference) | литерал `1` | обратная ссылка |
| `\x41`, `\u00e9`, `\0` | литералы `x`,`4`,`1` / `u`,`0`… | кодовая точка |
| `\f`, `\v`, `\e` | литералы `f`, `v`, `e` | управляющие символы |
| `*?`, `+?`, `??` (ленивые) | `?` после квантификатора молча съедается (стр. 410) → **жадное «наибольшее»** | минимально возможное |
| `)` без пары на верхнем уровне | `parse_seq` останавливается на `)`, **остаток шаблона отбрасывается** | ошибка |
| `(` без `)` | принимается без ошибки (стр. 545) | ошибка |
| `[[:word:]]`, `[[:graph:]]` и др. неизвестные POSIX-классы | класс никогда не совпадает, ошибки нет | ошибка |
| `a**`, `a+*` | принимается (цикл `while` в `parse_quantified`) | ошибка |
| `x{99999999999}` | `int`-переполнение (UB), далее раскрытие повторения копированием NFA без лимита | ошибка |
| `x{,5}` | `{` воспринимается как литерал | ошибка/литерал |

Особенно коварно **ленивое** `".*?"`: движок ищет самое длинное совпадение, и `/"[^"]*?"/` не опасен, а вот `/\/\*.*?\*\//` съест всё до *последнего* `*/` в файле. Автор грамматики привыкшего к PCRE/ECMAScript не получит ни ошибки, ни предупреждения.

**Рекомендации:**
1. Строгий парсер регулярок с кодами диагностик (`E0xxx unsupported regex construct`) и ссылкой на документированное подмножество.
2. Явно решить судьбу ленивых кванторов: либо ошибка «не поддерживаются: движок использует longest-match», либо предупреждение.
3. Поддержать (или осмысленно запретить) `\xNN`, `\uNNNN`, `\f`, `\v`, `\b` внутри класса (backspace), классы `\d\w\s` вне/внутри `[]`.
4. Лимиты: максимум `{n,m}`, максимум состояний NFA на токен (ошибка при превышении).
5. Таблицу «поддерживаемый синтаксис» — в README/AGENTS.md (сейчас её нет).

### C-03 🔴 📖 Нет ограничения глубины рекурсии в сгенерированном парсере

**Где:** рантайм в `codegen.cppm`: правила — обычные рекурсивные C-функции; в `ParsleyParser` нет счётчика глубины (поиск по `depth_limit`/`MAX_DEPTH` — пусто).

Библиотека (`.so/.dll`) предназначена для встраивания в чужие программы и разбора внешнего ввода. Вход вида `((((…` на несколько сотен тысяч уровней (или `[[[[…` для JSON-подобных грамматик) приведёт к **переполнению стека и SIGSEGV** — в процессе хоста.

**Исправление:** счётчик `p->depth` в каждом правиле (`if (++p->depth > PARSLEY_MAX_DEPTH) { record_failure("nesting too deep"); return false; }`), настраиваемый через `#define`/поле опций, плюс тест на 10⁵ вложений. То же касается рекурсивных функций самого компилятора (`first_of_prod`, `is_prod_nullable`, `emit_prod`, форматтер) — вход с очень глубоким выражением в `.parsley` может уронить `parsley` (проверить ❓).

### C-04 🔴 📖 Молчаливые лимиты в рантайме

**Где:** `codegen.cppm:1709–1713`, `1931`, `2161`, `2345`.

| Лимит | Что происходит при превышении |
|---|---|
| `PARSLEY_MAX_MODES = 64` | `push` режима **игнорируется** (`p_apply_mode_action`), но соответствующий `pop` потом снимает чужой режим → лексер выходит из вложенного режима раньше времени. Вложенность строк/интерполяций/HTML > 63 даёт неверные токены без ошибки. |
| `PARSLEY_MAX_CTX = 64` | `p_push_ctx` не добавляет привязку; последующий `exactly name` не находит значение → парсер «не принимает» валидный ввод (или принимает неверный). |
| `PARSLEY_MAX_PREFIX = 64` | `if (prefix_depth < MAX) push` — при переполнении пропуск записи сдвигает индексы в `p_prefix_get` → действие получает не те аргументы, **AST строится неверно, без ошибки**. |
| `PARSLEY_MAX_EXPECTED = 32` | усечение списка «ожидалось…» (безопасно, но не документировано) |

**Исправление:** выставлять «жёсткую» ошибку разбора (`parse error: nesting limit exceeded`) и/или делать стеки динамическими; значения лимитов вынести в `ParsleyOptions` или `#ifndef`-макросы.

### C-05 🔴 📖 Нет проверки результата выделения памяти

- `p_malloc` (`codegen.cppm:1317`) возвращает `malloc(...)` без проверки; `p_calloc` — так же. Вызывающие код (`1403, 1415, 1427, 1439, 1471, 1569–1570, 1944, 2393`) разыменовывают результат.
- `p_lex_all` (`1982`): `p->tokens = realloc(p->tokens, …)` — при NULL теряется исходный указатель и происходит разыменование NULL.
- `p_track` (`1776`): при провале `realloc` значение **не регистрируется** (утечка), но `p_track` всё равно возвращает `v` — вызывающий считает всё нормальным.
- `nfa_match_prefix` (`1567`) — 3 выделения на вызов, все без проверки.

При этом `AGENTS.md §5` утверждает: *«Zero unchecked `malloc`/`free`. All AST nodes, strings, and types reside in a caller-supplied memory arena»* — это **неверно** для `parser.c`: арена `psl_arena` существует только в сгенерированном семантическом слое (`codegen.cppm:4711+`), а AST парсера — это `malloc`-узлы с трекингом.

**Рекомендация (системная):** заменить россыпь `malloc` на единый аллокатор парсера — bump-арену на блоках с одной проверкой OOM и одним `free` в `parsley_result_free`. Это одновременно исправит C-05, уберёт массив `allocated[]` (8 байт накладных на каждый узел) и ускорит разбор. Либо ввести `p->oom` флаг, который прерывает разбор и возвращает `ParsleyResult{ok=false, error="out of memory"}`.

### C-06 🔴 📖 Запуск компилятора C: `std::system` + склейка командной строки

**Где:** `src/main.cpp:97–165`.

1. Команда собирается конкатенацией: `"\"" + cc + "\" … -I\"" + path + "\" …"` и выполняется `std::system`. Кавычки `"` в путях (допустимы в POSIX) ломают разбор; на POSIX внутри двойных кавычек остаются активными `$`, `` ` ``, `\` → путь вида `./out/$(cmd)` или `-o 'a"; rm …'` выполняет постороннюю команду. Каталог `-o` приходит из аргументов CLI, а имя модуля — из *содержимого грамматики* (см. M-07), т.е. от потенциально недоверенного файла.
2. `PARSLEY_CC` берётся из окружения и вставляется в командную строку как есть (аргументы типа `clang -fplugin=…` проходят).
3. Цепочка fallback: `clang` → `cc` → `gcc`; если сборка упала из-за **реальной ошибки в сгенерированном C** (как в C-01), `parsley` молча пробует следующий компилятор и печатает *одну* общую ошибку. Вывод первого компилятора мог уже пролететь в stderr — пользователь видит смесь.
4. Захардкожен путь автора: `D:/clang-23.1.3/bin/clang.exe` (`main.cpp:121–122`; так же в `ci.yml`).
5. `-std=c17 -O2` без `-Wall -Wextra -pedantic`, хотя `AGENTS.md` обещает «zero warnings»: предупреждения (как в C-01) остаются незамеченными.
6. `fs::exists(path)` без `error_code` (стр. 121, 158) может бросить исключение (нет прав на каталог).

**Исправление:** запуск процесса с вектором аргументов (`posix_spawnp` / `CreateProcessW` либо `boost::process`-подобная обёртка), `PARSLEY_CC` разбирать как исполняемый файл + аргументы явно, показывать stderr компилятора один раз и **не** переходить к следующему компилятору при ошибке компиляции (только при «команда не найдена»); добавить `-Wall -Wextra -pedantic` в режиме проверки (CI) и, желательно, ключ `--cc`.

### C-07 🔴 📖 Нет глобальной обработки исключений (CLI и LSP)

- `main.cpp:400`: `std::stoull(args[++i])` для `--fuzz`. Значение `abc` → `std::invalid_argument` → `std::terminate`/crash. Значение `-1` → `stoull` **принимает** и оборачивает в `18446744073709551615` → практически бесконечный fuzz. Нет верхней границы.

**Исправление:** обернуть тело `main` и цикл LSP в `try { … } catch (const std::exception&)`; парсить числа через `std::from_chars` с проверкой результата; ограничить `Content-Length` (например, 64 МБ); для LSP отвечать JSON-RPC-ошибкой `-32700/-32603`, а не падать.

## 3. Высокие находки

### H-01 🟠 📖 Один и тот же регекс-движок — в двух копиях, и они расходятся

`RegexParser`/`CharMatcher`/NFA есть и в `eval.cppm` (стр. 293–700), и в `codegen.cppm` (стр. 216–590). Различия уже есть:
- `\D`, `\W`, `\S` в `codegen` строятся через `std::isdigit/isalnum/isspace` (зависят от C-локали процесса), в `eval` — через явные диапазоны;
- `eval` использует `candidate_chars()` (только печатный ASCII 32–126 для генерации фаззером), `codegen` — битовые карты на 256 байт;
- комментарии и вспомогательные участки отличаются.

Следствие: `parsley test` (интерпретатор) и сгенерированный `parser.c` могут давать **разные результаты** на одном и том же примере. Плюс третья семантика — `std::regex(ECMAScript)` в LSP-playground (`tooling.cppm:1826`): там чередование «первое совпавшее» (leftmost-first), а не «самое длинное», так что `/a|ab/` на `ab` даст `a`, в сгенерированном парсере — `ab`.

**Рекомендация:** вынести в отдельный модуль `parsley.regex` (парсер → AST → NFA/DFA) и использовать его в `eval`, `codegen`, `tooling` (playground). Тогда исправления C-02/H-02 делаются один раз. Добавить property-тест «eval-лексер == скомпилированный C-лексер» на случайных вводах.

### H-02 🟠 📖 Регулярки байтовые — Unicode отсутствует

Все классы — 256-битные битовые карты по **байтам**. Следствия:
- `[а-я]` (UTF-8: `D0 B0` … `D1 8F`) разбирается как диапазон байт `B0..D1` + одиночные `D0`, `8F` — совпадает с обрывками многобайтных символов и с мусором;
- `[“”]` → набор из 4 байт, токен `/[“”]/` совпадает **с одним байтом** и режет символ пополам;
- `.` не знает кодпоинтов; `\w` — только ASCII; нет `\p{L}`, `\u`.
- `Parsley.Unicode` (`stdlib.cppm`) содержит только ASCII-классы (`alpha = /[a-zA-Z]/`, `space = /[ \t]/`) — название вводит в заблуждение.

Для «Python/Swift/Kotlin/Haskell» это существенно: идентификаторы в этих языках — Unicode (XID_Start/XID_Continue). Заявленные «complete» грамматики этого не поддерживают.

**Рекомендации:** компилировать UTF-8-диапазоны в последовательности байтовых NFA-узлов (как в `utf8-ranges`), поддержать `\uXXXX`, `\x{…}`, небольшой набор `\p{…}` (L, Lu, Ll, Nd, Zs, XIDS, XIDC); до тех пор — явная диагностика при non-ASCII внутри `[...]` и переименовать `Parsley.Unicode` → `Parsley.Ascii` (или честно документировать).

### H-03 🟠 📖 Стратегия разбора (`MODE …`) — декоративная

`grep` по `Strategy::`/`selected_strategy` показывает: значение попадает **только в комментарии** сгенерированного кода (`codegen.cppm:824, 1091, 3621`), в `README` проекта и в hover (`tooling.cppm:1630`), плюс валидацию E0500/E0510. Код генерируется один и тот же: рекурсивный спуск с упорядоченным выбором (PEG) и seed-growing для левой рекурсии. Не реализованы ни LL(k)/LALR(1)-таблицы, ни GLL/GLR.

При этом:
- `AGENTS.md §2.1`: «`{-# MODE LL1|LLk|LALR|PEG|GLL #-}`: **Forces parser execution strategy**» — неверно;
- Auto-режим сообщает «strategy: LL1 (grammar is LL(1) after left-factoring)» — а выполняется PEG-парсер, у которого семантика упорядоченного выбора отличается от LL(1) для неоднозначных грамматик;
- `{-# MODE LALR #-}` не даст LALR-сообщений о конфликтах, хотя пользователь вправе этого ожидать;
- `docs/Parsley — архитектура…` (v0.1) обещает несколько бэкендов (Haskell, Rust, TypeScript, Python) и алгоритмов — см. D-04.

**Рекомендация:** либо честно переименовать (`{-# PROFILE … #-}` = «набор проверок», PEG — единственная стратегия исполнения), либо реализовать. В любом случае исправить README/AGENTS/hover, чтобы они говорили «анализ/проверки», а не «стратегия исполнения».

### H-04 🟠 📖 Нет мемоизации → экспоненциальное время

Сгенерированный парсер — backtracking без packrat-таблицы (в `codegen.cppm` нет memo-структур; есть только запись для seed-growing левой рекурсии). Автоматический left-factoring решает случай *идентичных* префиксов, но не:
```haskell
stmt = assign | exprStmt           -- target "=" expr  |  expr
target = "(" target ")" | ident    -- вложенность повторяется в expr
expr   = "(" expr ")"   | ident
```
Каждый уровень вложенных скобок парсится дважды → `O(2^n)`. Python/Kotlin-грамматики из фикстур близки к такому виду (операторы-выражения vs присваивания, лямбды vs скобки).

**Рекомендации:** (1) packrat-мемоизация `(rule, offset[, mode, ctx_depth])` для правил без `context do` (включаемая прагмой `{-# MEMO #-}` или по умолчанию для правил, в которых найдено перекрытие FIRST-множеств); (2) подсчёт «потенциально экспоненциальных» мест в анализе и предупреждение; (3) бенчмарк-набор (глубокая вложенность 10/20/30 уровней).

### H-05 🟠 📖 Числа: локаль, точность, UB

- `token_to_value` (`codegen.cppm:1668–1674`): `strtoll`, `strtod` и `snprintf("%.15g")` (стр. 1497) зависят от текущей C-локали. Хост-приложение, вызвавшее `setlocale(LC_ALL, "")` (например, `de_DE`, `ru_RU`), получит `strtod("1.5") == 1.0` и вывод `1,5`. Для **разделяемой библиотеки** это серьёзный риск. Нужен локале-независимый разбор (`strtod_l`/`_strtod_l`, либо собственная реализация, либо `from_chars`-аналог в C).
- Тип `Int` хранится в `ParsleyValue` как `double` (`pv_number((double)iv, true)`): значения > 2^53 теряют точность (`9007199254740993` → `…992`). Для хэшей/ID/64-битных литералов это неверно. Нужны отдельные поля `int64_t`/`uint64_t`.
- `strtoll` при переполнении молча возвращает `LLONG_MAX` (проверка `errno` отсутствует).
- `snprintf(num_buf, …, "%lld", (long long)dv)` для `dv` вне диапазона `long long` — **неопределённое поведение** (стр. 1496: условие `v->is_int ||`).
- `PARSLEY_TOK_BOOL` принимает только `true` (в `eval` — `true`/`True`) — расхождение семантики.

### H-06 🟠 📖 Несовпадение форматов ожидаемого и фактического AST

`format_pattern_expected` (`codegen.cppm:3160–3170`) печатает не-целые числа через `std::ostream` с точностью по умолчанию (**6 значащих цифр**), а рантайм — `%.15g`. Тест `example "pi" : "3.14159265" parses-to Num 3.14159265` в сгенерированном `test_parser.c` даст `expected "Num 3.14159", got "Num 3.14159265"` и пометит корректный парсер как FAIL, хотя `parsley test` (eval) может пройти. Аналогично: управляющие символы в строках экранируются только для `\n \r \t \" \\` (остальные — «как есть»).

**Исправление:** единая функция форматирования и общий набор тестов-«золотых строк» для eval и C-рантайма (`%.15g` в обоих местах, одинаковая политика экранирования).

### H-07 🟠 📖 Лексер исходников `.parsley`: BOM, UTF-8, табы

- **BOM.** Нигде в `src/` нет обработки `EF BB BF` (поиск по `BOM`/`0xEF` пуст). Файл, сохранённый в Windows как «UTF-8 with BOM» (Блокнот, PowerShell `Out-File`, часть редакторов — а проект, судя по `D:/clang-…`, разрабатывается под Windows), даёт 3 ошибки `E0001 unexpected character` (по одной на байт) на первой строке. Нужно: `read_file_bytes` отбрасывает BOM, `read_text_file` — так же; LSP — также для `didOpen`.
- **Многобайтные символы вне строк/комментариев.** `switch (c)` на строке 406 создаёт `Invalid`-токен **на каждый байт** и отдельную диагностику со «сломанным» UTF-8 в сообщении (`unexpected character \`\xD0\``). Нужно потреблять целый кодпоинт и выдавать одну ошибку.
- **Табы.** `advance_char` (`lexer.cppm:~447–460`) увеличивает колонку на 1 для `\t`. Правило смещения (offside) сравнивает колонки, поэтому смешанные табы/пробелы или выравнивание табами дают неверные блоки без внятной ошибки. Варианты: табстоп 8 (как в Haskell-отчёте), либо диагностика «tabs are not allowed in layout».
- **Идентификаторы только ASCII** (`is_ident_start_lower/upper`, `lexer.cppm:~190`): `Привет`, `naïve` — ошибка. Допустимо, но не задокументировано.
- **Escape-последовательности в строках** (`lexer.cppm:601`): `\x`, `\u`, `\U`, `\e` и любой неизвестный `\c` молча превращаются в `c`; `"\x41"` даёт `x41`. Нужна ошибка `unknown escape`, а также поддержка `\xNN`/`\u{…}`.
- **`--` как комментарий** захватывает и операторные последовательности (`-->`), в отличие от Haskell, где `--` — комментарий, только если не продолжается символом-оператором.
- **Незакрытая `)` закрывает ВСЕ layout-блоки** (`apply_layout`, ветка `RParen`, условие `base_paren_depth >= paren_depth` при `paren_depth == 0`) → каскад ложных ошибок парсера после одной опечатки.
- `waiting_module_where` (`lexer.cppm:805, 856`) выставляется и сбрасывается, но нигде не читается — мёртвое состояние.
- `scan_regex` и `RegexParser::parse_char_class` расходятся: лексер завершает класс на первой `]`, парсер регулярок считает `]` первым символом литералом (`[]a]`, `[^]a]`); POSIX-класс `[[:alnum:]]` внутри лексера сбрасывает `in_class` на первой `]`, поэтому `/[[:alnum:]/]+/` обрывается на `/` внутри класса (`lexer.cppm:627–650`).

### H-08 🟠 📖 29 глобально зарезервированных слов

`classify_keyword` (`lexer.cppm:219–248`) превращает в ключевые слова: `module where import qualified as hiding data newtype foreign token skip keywords mode operators infixl infixr infix prefix postfix mixfix do pure context example parses-to fails-at expecting push pop`. Они не контекстные: правило, токен или поле AST по имени `prefix`, `postfix`, `mode`, `data`, `context`, `token`, `push`, `pop`, `example`, `pure`, `as` — **синтаксическая ошибка**. Это именно те слова, которые часто встречаются в реальных языках (`data class` в Kotlin, `prefix/postfix` в Swift, `as` в Python/Kotlin, `context`, `mode`).

В Haskell `as`, `qualified`, `hiding`, `forall` — не зарезервированы. **Рекомендация:** сделать слова контекстными (распознавать по позиции в декларации), либо опубликовать список зарезервированных слов в документации и добавить подсказку в диагностике («`prefix` is reserved, rename to `prefix_`»).

### H-09 🟠 📖 LSP-сервер (`tooling.cppm:2563–2610`)

- `if (!std::cin || content_length == 0) break;` — сообщение с `Content-Length: 0` (или заголовок, который клиент прислал без этого поля) **выключает сервер без ответа**.
- Нет защиты от огромного `Content-Length` (см. C-07).
- Заголовок `Content-Type` и другие — ок; но разбор регистронезависимости реализован, а проверка конца заголовков — нет (пустая строка до первого заголовка пропускается молча).
- Playground (`tooling.cppm:1826`) использует `std::regex` (ECMAScript) — см. H-01; в libstdc++ рекурсивная реализация может переполнить стек на длинных входах, а ловится только `regex_error`.
- Позиции в LSP — UTF-16 code units; сервер использует колонки в кодпоинтах (`lexer.cppm`). Совпадает для BMP, **расходится для эмодзи/символов вне BMP** (диагностики «уезжают»).
- `textDocumentSync = 1` (Full) и берётся *последний* `contentChanges[i]` — это корректно для Full, но стоит зафиксировать комментарием и тестом (при смене на Incremental код сломается).
- Конвейер на каждый `didChange` пересобирает всё (`update_document` → полный `compile`), без debounce/отмены; для больших грамматик (Kotlin ~11 КБ уже заметно) — лаги ввода ❓.

### H-10 🟠 📖 Несогласованные колонки: компилятор vs рантайм vs eval

Лексер самого DSL считает колонку **по кодпоинтам** (`lexer.cppm:456`), а в сгенерированном C `advance_line_col` (`codegen.cppm:1686`) увеличивает колонку **по байтам**; в `eval.cppm` обработки UTF-8 не найдено (поиск `0xC0/0x80/utf` пуст), т.е. вероятно, тоже по байтам. `example … fails-at (1, N)` для ввода с кириллицей получит разные `N` у разных реализаций/читателей. Дополнительно `p_current_loc` (стр. 1879) подставляет в сообщение **один байт** (`found "\xD0"`) — битый UTF-8 в тексте ошибки.

**Рекомендация:** выбрать одну модель (рекомендую: колонка = кодпоинт для сообщений, смещение = байт для API), зафиксировать в документации и реализовать везде; в сообщении «found» цитировать целый кодпоинт.

## 4. Средние и краевые случаи

### M-01 🟡 📖 Выбор стартового правила

`desugar.cppm:451–471`: 1) `START` на **несуществующее** правило молча игнорируется (проверка `contains`), без ошибки; 2) элементы экспорта, не являющиеся правилами, игнорируются; 3) если нет ни экспорта, ни `program`, берётся `gRules.begin()->first` — это **алфавитно первое** правило (`std::map`), а не первое объявленное. Грамматика `module M where` с правилами `atom`, `expr`, `stmt` получит старт `atom`. Нужны: ошибка `unknown START rule`, ошибка/предупреждение «нет явного старта», выбор по порядку объявления.

### M-02 🟡 📖 `NOFACTOR` и общий префикс

С `{-# NOFACTOR #-}` общий префикс альтернатив становится **ошибкой** E0214 «ambiguous alternatives» (`analysis.cppm:610–640`), хотя для упорядоченного выбора это не неоднозначность. Формулировка вводит в заблуждение. Кроме того, при автоматическом факторинге на каждое правило выпускается диагностика `E0214` уровня Note («this is resolved by left-factoring») — для больших грамматик это десятки строк шума в `check` ❓ (зависит от того, как `render_diagnostics` печатает Note). Рекомендация: отдельный код для «prefix overlap», Note — только под `-v`.

### M-03 🟡 📖 Производительность лексера в сгенерированном C

`nfa_match_prefix` (`codegen.cppm:1567`) на **каждый** вызов делает `malloc + malloc + calloc` (+ обнуление `seen[n]`), а вызывается в `p_lex_all` для **каждого токена на каждой позиции** (стр. 1960+) и в `p_scannerless_skip`/`p_match_token` ещё чаще. Сложность `O(позиции × токены × (аллокации + n_состояний))`. Дополнительно:
- `nfa_add_eps` — рекурсивная (глубина = длина ε-цепочки; для `[a-z]{0,5000}` — тысячи кадров);
- для `/"[^"]*"/` на незакрытой кавычке каждый вызов сканирует до конца файла → `O(N²)` на «плохих» входах;
- счётчик `mark` типа `int` переполнится на токене > 2³¹ байт (UB, практически недостижимо).

**Рекомендации:** (1) строить DFA на этапе генерации (subset construction) + таблицы переходов, один проход «maximal munch» по всем токенам режима одновременно — убирает множитель «число токенов»; (2) пока NFA — выделять рабочие буферы один раз на парсер/статически; (3) префильтр по первому байту.

### M-04 🟡 📖 Производительность анализа

`first_of_prod`/`is_prod_nullable` — рекурсивные, вызываются заново внутри неподвижных циклов, множества — `std::set<std::string>`, копируются по значению на каждый вызов (`analysis.cppm:697–830, 1224+`). В `propagate_follow` для каждого элемента последовательности пересчитывается `first_of_prod`. Сложность ≈ `O(итерации × размер_грамматики × размер_множества × длина_строки)`. Рекомендация: интернировать токены в `uint32_t`, использовать битовые множества (`std::vector<uint64_t>`) и рабочий список (worklist) вместо «пока что-то меняется». Заодно: «псевдотокены» `<ctx:name>` попадают в FIRST/FOLLOW и могут появиться в сообщениях о конфликтах/hover.

### M-05 🟡 📖 Память: все значения живут до конца разбора

`p_track` складывает в массив **все** созданные узлы, включая узлы неудачных веток; они освобождаются лишь в `parsley_result_free`. Пик памяти = число всех аллокаций за весь разбор (с откатами). Арена с откатом указателя (`mark/release` в `p_save/p_restore`) решила бы и эту проблему, и C-05.

### M-06 🟡 📖 `parse_int`/`parse_double` игнорируют ошибки

`parser.cppm:50–61`: `std::from_chars` без проверки результата, `strtod` без `errno`. Следствия: `infixl 99999999999 […]` → приоритет `0`, `fails-at (1, 99999999999)` → `0`, `1e999` → `inf`; ошибки не диагностируются. Лексер принимает `1e5` только после точки (`1.0e5`); `1e5` — это `IntLit(1)` + `LowerIdent(e5)`.

### M-07 🟡 📖 Преобразование имени модуля в имя артефактов

`to_lower` (`main.cpp:29–38`) заменяет всё не-алфавитно-цифровое на `_` (байты ≥0x80 — тоже, через `std::isalnum` для `unsigned char`). Последствия: `Foo.Bar` и `Foo_Bar` дают одно и то же имя (`foo_bar_parser`) → коллизии в проекте/пакете; модуль `Парсер` → `______` (6 подчёркиваний на 12 байт → `____…`); имя может **начинаться с цифры** (`2D` → `2d_parser` — недопустимый C-идентификатор и имя CMake-цели); совпадение с ключевыми словами C/макросами. Имя из грамматики идёт также в пути (`-o` по умолчанию) и в команду компилятора (см. C-06).

### M-08 🟡 📖 `parsley pkg init`

`tooling.cppm:2857+`: 1) имя пакета не валидируется (`../evil`, `my-lang`, `1abc`, пробелы) и подставляется в путь и в имя модуля; 2) `parsley.toml` **перезаписывается безусловно** (в отличие от остальных файлов, где есть `fs::exists`); 3) `parsley.toml` нигде больше не читается (grep: единственное упоминание — запись) → «пакетный менеджер» — только шаблонизатор; 4) при частичной ошибке остаются созданные файлы, ошибки записи `.psem`/`AGENTS.md`/`SKILL.md` молча игнорируются (`if (pf)` без else).

### M-09 🟡 📖 Фиксированные буферы в сгенерированных тестах

`char buf[4096]` (стр. 3236), `buf[1024]` (3312), `buf[512]` (3665): `parsley_format_ast` усекает вывод; сравнение с ожидаемым идёт по усечённой строке → **ложные FAIL** на больших AST; при `needed >= buf_size` результат не проверяется. Нужно использовать возвращаемое `needed` и динамический буфер.

### M-10 🟡 📖 CLI: мелочи

- `fmt --write --check` одновременно: молча побеждает `--check` (`main.cpp:531–560`); `--write` на `.psem` не проверяет идемпотентность форматтера. Форматтер `.psem` (`format_psl_module`) — это лишь обрезка пробелов/пустых строк (стр. 2620+), не «Ormolu-style».
- `parsley test --fuzz N`: фаззер запускается даже когда компиляция завершилась с ошибками, но `gRules` не пуст (`main.cpp:~423`).
- Нет `--no-color`/`NO_COLOR`, нет `--quiet`, коды выхода не документированы.
- `-b/--backend` (`ir-json`, `ir-sexpr`, `c17`, `c`), `-V`, `version`, `help` не отражены в README.
- `parsley build` на `.psem`-входе допустим (по help), но `parsley graph`/`agent-docs` на `.psem` — нет; README не поясняет.

### M-11 🟡 📖 Нулевые/пустые входы и Eof

- Пустой файл: layout пропускает `Eof` без ошибки; `parse_module` без `module` и деклараций → пустая грамматика → `determine_starts` не добавляет старт, `check` печатает ничего (нет «OK», `res.grammar.module_name.empty()`), а `build` формирует проект без правил ❓ — нужно явное `E0xxx empty module`.
- `parsley_parse("")`/`parsley_parse_n(NULL, 0)` — поведение с `NULL` и нулевой длиной в API не описано; `parsley_parse(const char*)` на строке с вложенным NUL останавливается на NUL (используйте `_n`) — стоит отметить в README/ABI.
- Входы с `\r\n`: `.` исключает и `\n`, и `\r` (`CharMatcher::match_any_non_nl`), а `skip comment = /--.*/` корректно завершится, но `[^\n]*` захватит `\r` — разные результаты для аналогичных записей.

### M-12 🟡 ❓ Сгенерированные проекты сборки

В отчёте не проверено (сборки нет), но стоит проверить: наличие `PARSLEY_BUILDING_DLL` в `CMakeLists/meson/xmake/bazel` для Windows; `-lm` только для Linux (macOS ок, но `BSD`/`MinGW`?); `.pc` с абсолютными путями; `Makefile` с `CC ?= cc`; версия `MODULE.bazel` (`bazel_dep`); `install(EXPORT)` отсутствует → `find_package(<mod>_parser)` не работает.

### M-13 🟡 📖 Семантика `Look`/`Rep` в анализе

`is_prod_nullable(Look)` всегда `true`, в том числе для `notFollowedBy`. Для FIRST у отрицательного lookahead — пустое множество; корректно (консервативно), но влияет на `check_alt_conflicts`: пара `notFollowedBy "x" *> "y"` и `"y"` выглядит как конфликт FIRST/FIRST ложно. Нужно тест-кейсы на `lookahead`/`notFollowedBy` в `check_alt_conflicts` ❓.

### M-14 🟡 📖 Левая рекурсия и контекстные правила

При `Auto` и левой рекурсии выбирается «LALR1» — но реализация (seed-growing, Warth) известна проблемами с **косвенной/взаимной** левой рекурсией и с приоритетами (результат зависит от порядка вызова правил). Для `context do` комбинируется с левой рекурсией ещё хуже (мемоизация по `(rule,pos)` игнорирует контекст). Нужны тесты на взаимную левую рекурсию (`a = b "x" | "y"; b = a "z" | "w"`), на левую рекурсию внутри `context do`, на левую рекурсию с `many`.

## 11. Что сделано хорошо

- Чёткая модульная архитектура и единый пайплайн; диагностики со span'ами, related-spans, подсказками, `explain`.
- Thompson-NFA вместо backtracking-регулярок: линейная сложность по длине токена и защита от катастрофического бэктрекинга; ε-циклы корректно обрабатываются штампами `seen[]` (нет бесконечного цикла на `(a*)*`).
- Seed-growing для левой рекурсии и возможность `context do` — редкая для генераторов парсеров функциональность.
- Самотесты в грамматике (`example`), фаззер, контрпримеры для конфликтов.
- В PSL-слое числовые преобразования (`std::stod`) обёрнуты в `try/catch` и дают диагностики (`PSL-CONFIDENCE`) — образец, который стоит применить в `parser.cppm`, `main.cpp`, `tooling.cppm`.
- Аккуратная проверка соответствия тега и `VERSION` в `release.yml` (учтён `\r`).
